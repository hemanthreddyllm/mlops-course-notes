Chapter 21 · Kubernetes

Kubernetes: run containers so they keep running

Docker packages one container; Kubernetes runs many of them across a cluster of machines and keeps them alive. The instructor covers what it is (open source, from Google, 2014), its four selling points — load balancing, scaling, storage and self-healing — and then deploys a Flask model app to Google Kubernetes Engine: build the image, push it to Google's registry, create a cluster, kubectl create deployment, expose it with a LoadBalancer, open the external IP, and delete everything afterwards.

01What Kubernetes is 10:18:11

The instructor's definition: a powerful open-source system, developed by Google and released in 2014, for managing containerised applications. In plainer words: a system for running and coordinating containers across a cluster of machines, which manages the whole lifecycle of those containers.

What you already have (Chapter 16–18)

One Docker image, started by hand or by a CI job with docker run on a single EC2 machine. If that container dies, or the machine dies, or traffic doubles, you fix it.

What Kubernetes adds

You declare "I want 3 copies of this image, reachable on port 80". The cluster keeps that true: restarting containers, replacing them, spreading traffic and adding copies when load rises.

The one idea behind everything

Kubernetes is declarative. You describe the desired state; controllers constantly compare it with the real state and act on the difference. You never say "start a container" — you say "three should exist", and something else works out how.

Kubernetes is often written K8s ("k", eight letters, "s"). The name is Greek for helmsman, which is where the ship's-wheel logo comes from. It was donated to the Cloud Native Computing Foundation in 2015.

02The four features, and what each really needs 10:19:14

The video lists four benefits. Each is real, but each needs something in your configuration before it works:

Feature (from the video)What it meansWhat you must provide
Load balancing
"automatically distributes the load between the containers"		A Service gives the pods one address and spreads connections across them.A Service, and more than one replica. With a single pod there is nothing to balance.
Scaling
"scale up or down at peak hours, weekends and holidays"		Add or remove pods as demand changes.A HorizontalPodAutoscaler plus CPU requests in the pod spec. Without an HPA, the replica count never changes on its own.
Storage
"keep storage consistent with multiple instances"		Disks that outlive a pod, and can be shared or mounted per replica.A PersistentVolumeClaim (and a StatefulSet for per-replica disks). Containers are otherwise wiped clean on every restart.
Self-healing
"restarts containers that fail, kills ones that don't respond to health checks"		Crashed pods come back; unhealthy containers are restarted; pods on a dead node are recreated elsewhere.A Deployment (so a ReplicaSet is counting) and liveness / readiness probes. Without probes, a hung-but-alive process is left running.
Careful with "everything is automatic"

The video says you don't have to worry about load balancing or scaling because Kubernetes handles it. What it really gives you is the machinery. A plain kubectl create deployment, as in the demo, has one replica, no probes, no resource requests and no autoscaler, so none of the four features is actually doing anything yet. The manifests in the hands-on project fill all of that in.

The reconciliation loop, concretely

You apply a Deployment asking for 3 replicas of api:v2:

  1. The Deployment controller creates a ReplicaSet for v2.
  2. The ReplicaSet controller sees 0 pods but wants 3, and creates 3 pod objects.
  3. The scheduler sees 3 pods with no node and assigns each to a node with room.
  4. Each node's kubelet pulls the image, starts the container and runs the probes.
  5. When a pod passes its readiness probe, the endpoint controller adds it to the Service, and traffic starts flowing.

Kill a pod and the same loop replaces it within seconds. That's all "self-healing" is.

05The video's demo on GKE, step by step 10:20:18

The instructor uses Google Cloud here, not AWS, because GKE makes a cluster easy and "a local Kubernetes on Windows causes lots of setup issues and takes a lot of space". A new Google Cloud account gets $300 in free credit, which is plenty for this.

The app is a ready-made PyCaret example: a Flask page that predicts medical insurance charges from age, sex, BMI, children, smoker and region — a regression model, with templates/, static/, a training notebook, a saved model and a Dockerfile. Any containerised app would do.

  1. Enable the services: search for Container Registry and enable it (this is where images go, "like Docker Hub"), then Kubernetes Engine and enable that too.

  2. Open Cloud Shell from the console (a free Linux terminal with gcloud, docker and kubectl already installed), and check you're in the right project.

  3. Clone and set the project id:

    git clone <the app repo> && cd <repo>
export PROJECT_ID=<your-project-id>      # shown in the console header

  4. Build the image, tagged so it can be pushed to Google's registry:

    docker build -t gcr.io/$PROJECT_ID/insurance-app:v1 .

    This failed twice in the video, and the fixes are worth remembering: the Dockerfile's Python 3.7 base was too old for the requirements (changed to 3.9), and a pinned PyCaret version no longer installs (the pin was removed). "Old packages get deprecated — take care of that when you build the image."

  5. Push it:

    gcloud auth configure-docker gcr.io       # let docker log in to the registry
docker push gcr.io/$PROJECT_ID/insurance-app:v1
docker images                             # check it locally

    The image then appears in Container Registry.

  6. Create the cluster (console or CLI). In the console: name it, pick a region (us-central1), choose the Standard tier rather than Enterprise, and create. It takes about 5 minutes until the status turns green.

    gcloud config set compute/zone us-central1
gcloud container clusters create ml-cluster --num-nodes=1   # more nodes = more cost

  7. Deploy and expose:

    kubectl create deployment insurance-app --image=gcr.io/$PROJECT_ID/insurance-app:v1
kubectl expose deployment insurance-app --type=LoadBalancer --port 80 --target-port 8080
kubectl get service                      # wait for EXTERNAL-IP

    The app listens on 8080 inside the container; the Service publishes it on port 80. Open http://<external-ip>, fill in the form, click Predict, and the model answers. "Now load balancing and scaling are handled automatically."

  8. Delete everything 10:44:36: select the cluster → Delete → type its name to confirm; then delete the image from the registry. "Make sure you delete it if you're not using it, otherwise it will charge you."

08Rollouts and autoscaling, measured

09When Kubernetes is worth it

Good reasons

  • Many services, or many teams, sharing infrastructure.
  • You need rolling updates, health checks, autoscaling and self-healing as standard behaviour.
  • GPU scheduling and batch jobs beside online serving.
  • You want the same setup on any cloud, or on-premises.
  • The ML platform you want runs on it: KServe or Seldon for serving, Kubeflow or Argo for pipelines, Ray for distributed training.

Reasons to wait

  • One small model API with modest traffic. The cluster costs more than the app, and you now own YAML, upgrades, RBAC and networking.
  • Simpler options do the same job: Cloud Run, AWS App Runner, ECS Fargate, Azure Container Apps, or a managed endpoint such as SageMaker or Vertex AI. They give scaling, health checks and rolling deploys with no cluster.
  • Nobody on the team has operated a cluster before.

For interviews, that trade-off matters more than the commands: Kubernetes is the general answer, and the managed services are the pragmatic one for a single model.

10Precision notes

  • Container Registry (gcr.io) is deprecated. Google has moved to Artifact Registry (<region>-docker.pkg.dev/<project>/<repo>/<image>), which the instructor briefly calls it by name. New projects should push there; gcloud auth configure-docker <region>-docker.pkg.dev.
  • "Everything is automatic" needs configuration. The demo deploys one replica with no probes, no resource requests and no HPA, so there is nothing to load-balance across, nothing to restart on a hang, and nothing to scale. See section 2.
  • Imperative commands don't survive. kubectl create deployment and kubectl expose leave no record of what the cluster should look like. Keep manifests in git and kubectl apply -f; you also get diffs, reviews and rollbacks.
  • `latest`-style tags and :v1 by hand. Tag images with the commit SHA (as Chapter 18's workflow does) so you can tell what's running and roll back precisely.
  • The image size claim. The instructor says the push is "around 140 GB"; a PyCaret image is more like 1–4 GB. Still large: use slim bases and multi-stage builds, since every node pulls the image.
  • One node, one replica, one point of failure. --num-nodes=1 is fine for a demo, but a node upgrade or failure then takes the app down. Use at least 2–3 nodes across zones, plus a PodDisruptionBudget.
  • Cost adds up quietly: the GKE control plane (about $0.10/hour per cluster beyond the free one), the node VMs, the cloud load balancer, stored images and any leftover persistent disks. The video's advice to delete the cluster is the important part; also delete the Service (it owns the load balancer) and the images.
  • Security defaults are weak. A plain deployment runs as root with no limits. Set runAsNonRoot, drop capabilities, add a read-only root filesystem and resource limits, and use Workload Identity instead of service-account keys. Our manifest does all of these.
  • No health checks means no self-healing. Kubernetes restarts a container that exits, but a process that's alive yet stuck is only caught by a liveness probe. A readiness probe is what keeps traffic off a pod that is still loading a model.
  • Memory limits kill containers. Exceed the memory limit and the pod is OOMKilled and restarted; exceed the CPU limit and it is merely throttled. Model servers often need a generous memory limit and a modest CPU request.
  • The app in the demo is a Flask dev server in one container behind a public load balancer. In production, use gunicorn or uvicorn workers (our image does) and put an Ingress with TLS in front.
  • Deleting the cluster doesn't delete everything. Load balancers, static IPs, disks made by PVCs and registry images can survive it. Check the billing page a day later.

11Interview questions

What problem does Kubernetes solve that Docker doesn't?

Docker builds and runs a container on one machine. Kubernetes runs many containers across many machines and keeps them in the state you asked for: scheduling them onto nodes, restarting failures, replacing pods when a node dies, rolling out new versions gradually, load-balancing traffic, scaling on demand, and managing config, secrets and storage. Docker is the packaging; Kubernetes is the operations.

Explain Pod vs ReplicaSet vs Deployment.

A Pod is one running instance (one or more containers sharing a network namespace). A ReplicaSet keeps a fixed number of identical pods alive. A Deployment manages ReplicaSets over time: on an update it creates a new one and shifts pods over gradually, keeping the old one around so kubectl rollout undo works. You write the Deployment; the other two are created for you.

Readiness vs liveness vs startup probes?
  • Readiness: "can I serve traffic?" Failing removes the pod from the Service, but doesn't restart it. Use it while a model loads.
  • Liveness: "am I still working?" Failing restarts the container. Use it for deadlocks and hangs.
  • Startup: protects a slow starter — the other two only take effect after it passes.

A common mistake is a liveness probe that's too aggressive on a slow-loading model server, which puts it in a restart loop.

How does a request reach a pod?

Client → cloud load balancer (for a type: LoadBalancer Service) or Ingress → a node → kube-proxy's rules (iptables or IPVS) → one of the Service's endpoints, which are the ready pods matching its label selector → the container's targetPort. Inside the cluster, other pods just use the DNS name service.namespace.svc.cluster.local.

How do rolling updates work, and how do you roll back?

Changing the pod template creates a new ReplicaSet. The Deployment scales it up and the old one down, respecting maxSurge (extra pods allowed) and maxUnavailable (how many may be missing). With maxUnavailable: 0 a new pod must become ready before an old one goes. If new pods never become ready, the rollout stalls at the progress deadline and the old version keeps serving. kubectl rollout undo goes back to the previous revision (kept up to revisionHistoryLimit).

Requests vs limits, and how do they relate to autoscaling?

Requests are what the scheduler reserves and what the HPA measures utilisation against; limits are the ceiling (over the memory limit the container is OOMKilled; over the CPU limit it's throttled). No requests means no sensible scheduling and no CPU-based autoscaling. The HPA scales pods; the Cluster Autoscaler adds nodes when pods can't be placed; VPA tunes the requests themselves.

A pod is stuck in Pending / CrashLoopBackOff / ImagePullBackOff. What do you do?
  • Pending: nothing can schedule it — not enough CPU or memory, a node selector or taint that doesn't match, or an unbound PVC. kubectl describe pod shows the scheduler's reason.
  • ImagePullBackOff: wrong image name or tag, or missing registry credentials (imagePullSecrets, or Workload Identity).
  • CrashLoopBackOff: the container keeps exiting — read kubectl logs --previous; often a missing env var, a missing file, or a too-strict liveness probe.
How would you serve an ML model on Kubernetes?

Simplest: containerise the API (Chapter 17), keep the model in the image or pull it from a registry or bucket at startup, then Deployment + Service + HPA + probes, as in our manifests. At larger scale, use a serving layer such as KServe or Seldon for canary traffic splitting, autoscaling to zero and standard inference protocols; schedule GPUs with node selectors and resource limits; run pipelines with Kubeflow or Argo; and keep the model registry (MLflow) as the source of truth for which version is deployed.

What runs in the control plane?

API server (the only entry point, with auth and validation), etcd (the state store), scheduler (assigns pods to nodes) and controller manager (the reconciliation loops), plus a cloud controller for load balancers and disks. Each node runs a kubelet (starts containers, runs probes), kube-proxy (service networking) and a container runtime such as containerd. Managed services (GKE, EKS, AKS) run the control plane for you.

12Recap

  • What: Kubernetes (Google, 2014, open source) runs containerised apps across a cluster and manages their whole lifecycle. You declare the desired state; controllers make it true.
  • Features: load balancing, scaling, storage and self-healing — each needs a Service, an HPA with CPU requests, a PVC, and probes respectively.
  • Pieces: control plane (API server, etcd, scheduler, controllers) and nodes (kubelet, kube-proxy, runtime). Objects: Pod → ReplicaSet → Deployment, plus Service, Ingress, ConfigMap/Secret, PVC, HPA, Namespace, Job.
  • The demo: enable Container Registry and Kubernetes Engine → Cloud Shell → clone → export PROJECT_ID → docker build -t gcr.io/$PROJECT_ID/insurance-app:v1 . → gcloud auth configure-docker → docker push → create a cluster (about 5 min) → kubectl create deployment → kubectl expose --type=LoadBalancer --port 80 --target-port 8080 → open the external IP → predict.
  • Build failures to expect: an outdated Python base image and pinned library versions that no longer install.
  • Prefer manifests in git over one-off commands, and add probes, resource requests, an HPA and a non-root security context.
  • Delete the cluster, the Service and the images when you're done, or the bill keeps running.
