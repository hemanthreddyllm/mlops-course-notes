01Why branches? 02:22:04

The instructor's scenario: another team is assigned to your project. You want the current repository (main) to stay as it is, but the new work still has to happen somewhere. The answer is a branch: a separate line of development where changes don't affect main.

02List branches: git branch 02:22:04

$ git branch

Beyond the video: git branch -a also lists remote branches (remotes/origin/…).

03Create and switch: git checkout -b 02:22:04

The instructor considers naming it something like new-feature, then uses his own name, bappy.

~/github-learning-test (main)
$ git checkout -b bappy      # -b = create the branch, then switch to it

  main

git checkout -b name

What the video uses. It creates the branch from the commit you're on and switches to it.

git switch -c name

Beyond the video: the newer equivalent. switch only changes branches, whereas checkout also restores files, so it's harder to misuse.

Naming branches in real teams

Name branches after the work, not the person: feature/drift-monitoring, fix/scaler-nan, exp/xgboost-tuning. Many CI setups use these prefixes to decide what to run.

04Commit and push to the new branch 02:23:07

On bappy, the instructor edits test3.py (a hello-world print plus "this is new"), then runs the Chapter 09 cycle. The only difference is the branch name in the push.

~/github-learning-test (bappy)
$ git add .
$ git commit -m "new code added"
$ git push origin bappy      # push to the NEW branch, not main
To https://github.com/<you>/github-learning-test.git
 * [new branch]      bappy -> bappy

On GitHub, the repo page still shows main by default. Open the branch dropdown and choose bappy: there test3.py contains the new code. On main it doesn't.

Tip

git push -u origin bappy also sets the upstream, so afterwards plain git push and git pull know which remote branch to use. GitHub also shows a "Compare & pull request" banner after you push a new branch. That's where merging starts (below).

05Switch back: main is untouched 02:24:11

~/github-learning-test (bappy)
$ git checkout main
Switched to branch 'main'
$ cat test3.py
                                # empty: the change exists only on bappy

Switching branches changes the files in your folder to match that branch. Try it:

$ git checkout
📄 test3.py
📄 test.pysame on both branches
print("feature 1")
print("feature 2")
The point of the demo

You changed code without modifying the main code. The branch took the change, and main stayed exactly as it was. Many branches can carry different work at the same time.

Watch out

Commit (or git stash) your work before switching. Git refuses to switch if uncommitted changes would be overwritten. Uncommitted, non-conflicting changes stay in your folder and come with you to the other branch.

The instructor goes back to TensorFlow's GitHub repo, which has many branches. A package that large can't have everyone committing straight to the main line, so work happens on separate branches and releases are made from them (TensorFlow keeps release branches such as r2.17).

07Merging and pull requests

What the video doesn't cover

A branch is only useful if its work eventually reaches main. The video never merges bappy, so here are the two ways to do it.

OPTION A · LOCAL

git merge

git checkout main
git pull                 # be up to date
git merge bappy          # bring bappy's commits in
git push origin main
git branch -d bappy      # optional cleanup
OPTION B · TEAMS USE THIS

Pull request (PR) on GitHub

  1. Push the branch (done in the video).
  2. Click Compare & pull request: base main ← compare bappy.
  3. Teammates review the diff and comment. CI runs tests automatically.
  4. Click Merge pull request, then delete the branch.
  5. Locally: git checkout main && git pull.

08Merge conflicts

If main and bappy both changed the same lines of test3.py, Git can't decide which to keep, so it stops and marks the file:

test3.py during git merge bappy
<<<<<<< HEAD
print("hello from main")
=======
print("hello world, this is new")
>>>>>>> bappy
  1. Edit the file to the version you want (keep one side, the other, or both) and delete the marker lines. VS Code offers Accept Current / Incoming / Both buttons.
  2. git add test3.py
  3. git commit (Git pre-fills the merge message), then git push.

Pull often and keep branches short-lived: small, frequent merges mean fewer and simpler conflicts. git merge --abort cancels a merge that went wrong.

09Branching workflow for ML projects

Beyond the video · a practical setup
BranchPurposeWhat CI/CD does
mainAlways deployable. Protected: changes only through reviewed PRs.Build the Docker image → deploy to production
feature/*, fix/*One task each, short-lived, merged by PRTests, lint, a quick training smoke test
exp/*Model experiments (new algorithm, features)Run the pipeline, log metrics to MLflow, post them in the PR
tags v1.2.0Mark released versionsTag the image and model with the version for rollback

This is GitHub Flow (short feature branches plus PRs into main), the most common model for small and medium teams. Git Flow adds long-lived develop and release branches for projects with scheduled releases. On GitHub, set up branch protection on main (Settings → Branches) to require reviews and passing checks.

11Interview questions

What is a branch in Git, technically?

A lightweight, movable pointer to a commit. Creating one only writes a small reference, which is why branching is cheap. HEAD points to the branch you're currently on, and each new commit moves that branch forward.

Merge vs rebase?

merge joins histories with a merge commit and preserves exactly what happened. rebase replays your commits on top of the target branch, giving a linear history but rewriting commit IDs. Rule of thumb: rebase your own unpushed branch to tidy it; never rebase commits others already have.

How do you resolve a merge conflict?

Open the conflicted files, choose the correct content between the <<<<<<<, ======= and >>>>>>> markers, remove the markers, run the tests, git add the files and commit. If needed, git merge --abort returns to the pre-merge state.

What is a pull request and why use one?

A request on GitHub to merge one branch into another. It gives code review, discussion, a visible diff, and automated CI checks before anything reaches main. With branch protection it's the only way to change production code.

Describe a branching strategy for an ML team.

GitHub Flow: protected main that is always deployable, short-lived feature/ and exp/ branches, and PRs that trigger tests plus a pipeline run with metrics logged to MLflow. Merging to main triggers CD to build and deploy, and releases are tagged so models and images can be rolled back.

git checkout vs git switch?

checkout is overloaded: it switches branches and restores files. Git 2.23 split it into switch (branches: switch -c creates) and restore (files). Both still work.

You committed to main by mistake instead of a feature branch (not pushed yet). Fix it.

git branch feature/x (keeps the commit on a new branch), git reset --hard origin/main (moves main back to the remote), then git switch feature/x. Since nothing was pushed, rewriting local main is safe.

12Recap

  • Branches let another team, or you, add work without changing main.
  • git branch lists branches. git checkout -b bappy creates one and switches to it.
  • Commit as usual, then git push origin bappy. On GitHub, pick the branch from the dropdown to see its code.
  • git checkout main switches back, and the files return to main's version (test3.py is empty there).
  • Large projects like TensorFlow use many branches. These basics are enough for the course.
  • Beyond the video: finish a branch with git merge or, in teams, a pull request with review and CI. Resolve conflicts by editing the marked lines.
