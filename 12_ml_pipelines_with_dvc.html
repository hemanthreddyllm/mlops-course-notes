04Why convert it: modular components 02:45:54

This is the "traditional approach" from Chapter 03, and it has the same problems: everything is in one place, so there's no modularity. That makes the code hard to manage, hard to collaborate on, and hard to extend with new features.

Notebook vs production

The notebook is for experimenting: checking that everything works. For production, split the code into separate components and build a pipeline. This demo uses simple functions. Later projects in the course use full OOP modular code with classes.

05The five component files 02:46:57

Inside src/, each notebook section becomes its own script with the same logic, wrapped in functions and called from main(). The instructor also adds logging, so messages and errors go to a log file instead of only the terminal (logging is covered in detail later). Each script reads the previous stage's files and writes its own:

# src/data_ingestion.py  →  data/raw/train.csv, test.csv
import os, logging
import pandas as pd
from sklearn.model_selection import train_test_split

logging.basicConfig(filename="pipeline.log", level=logging.INFO)
DATA_URL = "https://raw.githubusercontent.com/entbappy/Branching-tutorial/refs/heads/master/tweet_emotions.csv"

def load_data(url):
    return pd.read_csv(url)

def preprocess(df):
    df = df.drop(columns=["tweet_id"])
    df = df[df["sentiment"].isin(["happiness", "sadness"])].copy()
    df["sentiment"] = df["sentiment"].map({"happiness": 1, "sadness": 0})
    return df

def save(train, test, out_dir="data/raw"):
    os.makedirs(out_dir, exist_ok=True)
    train.to_csv(f"{out_dir}/train.csv", index=False)
    test.to_csv(f"{out_dir}/test.csv", index=False)

def main():
    try:
        df = preprocess(load_data(DATA_URL))
        train, test = train_test_split(df, test_size=0.2, random_state=42)
        save(train, test)
        logging.info("ingestion done: %d train / %d test rows", len(train), len(test))
    except Exception:
        logging.exception("ingestion failed"); raise

if __name__ == "__main__":
    main()
# src/data_preprocessing.py  data/raw  →  data/processed
import os, re, string
import pandas as pd, nltk
from nltk.corpus import stopwords
from nltk.stem import WordNetLemmatizer

nltk.download("stopwords", quiet=True); nltk.download("wordnet", quiet=True)
STOP, LEM = set(stopwords.words("english")), WordNetLemmatizer()

def normalize(text):
    text = str(text).lower()
    text = re.sub(r"https?://\S+|www\.\S+", "", text)       # URLs
    text = re.sub(r"\d+", "", text)                          # numbers
    text = text.translate(str.maketrans("", "", string.punctuation))
    words = [LEM.lemmatize(w) for w in text.split() if w not in STOP]
    return " ".join(words)

def main():
    os.makedirs("data/processed", exist_ok=True)
    for split in ("train", "test"):
        df = pd.read_csv(f"data/raw/{split}.csv")
        df["content"] = df["content"].map(normalize)
        df.dropna().to_csv(f"data/processed/{split}_processed.csv", index=False)

if __name__ == "__main__":
    main()
# src/feature_engineering.py  data/processed  →  data/features
import os, pickle
import pandas as pd
from sklearn.feature_extraction.text import CountVectorizer

def main(max_features=1000):
    train = pd.read_csv("data/processed/train_processed.csv").fillna("")
    test  = pd.read_csv("data/processed/test_processed.csv").fillna("")
    vec = CountVectorizer(max_features=max_features)           # bag of words
    X_train = vec.fit_transform(train["content"])              # fit on TRAIN only
    X_test  = vec.transform(test["content"])
    os.makedirs("data/features", exist_ok=True)
    for name, X, y in (("train", X_train, train["sentiment"]), ("test", X_test, test["sentiment"])):
        out = pd.DataFrame(X.toarray()); out["label"] = y.values
        out.to_csv(f"data/features/{name}_bow.csv", index=False)
    pickle.dump(vec, open("data/features/vectorizer.pkl", "wb"))  # needed at serving time

if __name__ == "__main__":
    main()
# src/model_building.py  data/features  →  model.pkl
import pickle
import pandas as pd
from xgboost import XGBClassifier

def main():
    df = pd.read_csv("data/features/train_bow.csv")
    X, y = df.drop(columns=["label"]).values, df["label"].values
    model = XGBClassifier(eval_metric="logloss")
    model.fit(X, y)
    with open("model.pkl", "wb") as f:
        pickle.dump(model, f)

if __name__ == "__main__":
    main()
# src/model_evaluation.py  model.pkl + test features  →  metrics.json
import json, pickle
import pandas as pd
from sklearn.metrics import accuracy_score, precision_score, recall_score, roc_auc_score

def main():
    model = pickle.load(open("model.pkl", "rb"))
    df = pd.read_csv("data/features/test_bow.csv")
    X, y = df.drop(columns=["label"]).values, df["label"].values
    pred, proba = model.predict(X), model.predict_proba(X)[:, 1]
    metrics = {
        "accuracy":  accuracy_score(y, pred),
        "precision": precision_score(y, pred),
        "recall":    recall_score(y, pred),
        "auc":       roc_auc_score(y, proba),
    }
    json.dump(metrics, open("metrics.json", "w"), indent=4)

if __name__ == "__main__":
    main()

06How the stages depend on each other 02:52:18

The five stages must run in order, because each one needs the previous one's output. You can't run evaluation right after ingestion. That chain of dependencies is what makes it an ML pipeline.

07Writing dvc.yaml 02:53:20

DVC reads the pipeline from a file named dvc.yaml in the project root, as the DVC docs specify.

Why YAML?

Most configuration files in DevOps and MLOps are YAML (DVC, Kubeflow, GitHub Actions, Kubernetes, Docker Compose…) because it's easy to write and read. The instructor expands it as "Yet Another Markup Language", its original name. Today's official expansion is "YAML Ain't Markup Language".

Before using DVC, the instructor deletes all generated outputs (data folder, log, metrics, model) so DVC can recreate them. Every stage has the same three keys:

cmd

The shell command that runs the stage.

deps

What the stage depends on: its own script (if the script is missing there's nothing to run) plus its input data.

outs

What the stage produces. A later stage can list it as a dependency.

The final file, built one stage at a time during the video:

stages:
  data_ingestion:
    cmd: python src/data_ingestion.py
    deps:
      - src/data_ingestion.py
    outs:
      - data/raw

  data_preprocessing:
    cmd: python src/data_preprocessing.py
    deps:
      - data/raw
      - src/data_preprocessing.py
    outs:
      - data/processed

  feature_engineering:
    cmd: python src/feature_engineering.py
    deps:
      - data/processed
      - src/feature_engineering.py
    outs:
      - data/features

  model_building:
    cmd: python src/model_building.py
    deps:
      - data/features
      - src/model_building.py
    outs:
      - model.pkl

  model_evaluation:
    cmd: python src/model_evaluation.py
    deps:
      - model.pkl
      - src/model_evaluation.py
    metrics:                 # not "outs": lets `dvc metrics show` read it
      - metrics.json
The one rule

"You just need to understand your pipeline: what is the input and what is the output of each step." Once you know each stage's dependencies and outputs, you can write the dvc.yaml for any pipeline.

Beyond the video · the run-cache

When you switch the code back to a version DVC has already run, recent DVC versions may say "Stage … is cached - skipping run, checking out outputs". DVC's run-cache remembers earlier results and restores them without recomputing.

What it would cost without DVC

If you run the five Python files yourself, all five run every time. For a deep learning project that means paying for GPU training even when nothing changed. So whenever you build a pipeline and set up retraining, add DVC to track it.

1 · Move hyperparameters into params.yaml

# params.yaml
feature_engineering:
  max_features: 1000
model_building:
  n_estimators: 100
  learning_rate: 0.1

# dvc.yaml (stage excerpt)
model_building:
  cmd: python src/model_building.py
  deps: [data/features, src/model_building.py]
  params:
    - model_building.n_estimators
    - model_building.learning_rate
  outs: [model.pkl]

Now changing only a parameter re-runs only the stages that use it. Read the values in Python with yaml.safe_load(open("params.yaml")) (that's what pyyaml in requirements.txt is for).

2 · Compare experiments

dvc metrics diff      # metrics vs the last commit
dvc params diff

3 · Beyond the video: change one hyperparameter and compare

After committing, n_estimators was raised from 100 to 300. dvc repro re-ran only model_building and model_evaluation, and dvc metrics diff reported:

Found while building this · pandas 3

The course repo's ingestion code does final_df['sentiment'].replace({...}, inplace=True) on a filtered slice. With pandas ≥ 3 (copy-on-write), that in-place change does nothing, and the labels would stay as text. The project here uses df = df[...].copy() plus .map({...}), which works on every version.

14Interview questions

Explain dvc.yaml and dvc.lock.

dvc.yaml is the pipeline definition you write: stages with cmd, deps, outs, params and metrics. dvc.lock is generated by dvc repro and records the hashes and sizes of every dependency and output from the last run. DVC compares the current state with the lock file to decide which stages to skip. Both are committed to Git.

How does DVC know a stage needs to re-run?

It hashes each stage's dependencies (scripts, input files and folders, listed params) and outputs, and compares them with dvc.lock. If anything differs, or an output is missing, the stage runs. Its new outputs then change the dependencies of downstream stages, so those run too. Unchanged stages are skipped, or restored from the run-cache.

Your ingestion stage downloads from a URL. New rows appear upstream but dvc repro skips the stage. Why, and how do you fix it?

DVC only tracks what's declared. The stage's only dependency is the script, which didn't change. Fixes: use dvc import-url plus dvc update so the remote file is tracked; add always_changed: true to that stage; or make the data version an explicit parameter (such as a date or snapshot ID in params.yaml).

What's the difference between outs and metrics in dvc.yaml?

Both are tracked outputs. Files under metrics are also treated as metric files, so dvc metrics show and dvc metrics diff can read and compare them across commits and experiments. Usually they're small JSON or YAML files kept in Git rather than the DVC cache.

Why split a notebook into components before adding a pipeline tool?

Each component gets clear inputs and outputs, so it can be run, tested and owned on its own, reused, and declared as a pipeline stage with dependencies. A notebook has hidden state and no boundaries, so a tool can't tell what depends on what.

Where do the vectorizer and model go for serving?

Both are pipeline outputs. The fitted CountVectorizer must be saved alongside the model so the prediction pipeline applies the same transformation to new text. They're versioned with DVC (or registered in MLflow) and loaded by the API at startup.

How would you run this pipeline automatically?

A CI/CD job (for example GitHub Actions on push, or on a schedule) runs dvc pull → dvc repro → dvc push, posts dvc metrics diff on the pull request, and, if the metrics pass a threshold, promotes the model and triggers deployment.

15Recap

  • Setup: conda environment (Python 3.11) → pip install -r requirements.txt (includes dvc) → VS Code.
  • The notebook (Twitter emotion: happiness 1 / sadness 0, NLTK cleaning, CountVectorizer, XGBoost, accuracy/precision/recall) is the experiment. Production needs modular components.
  • src/: ingestion → data/raw, preprocessing → data/processed, feature engineering → data/features, model building → model.pkl, evaluation → metrics.json, with logging to a file.
  • dvc.yaml: one stage each, with cmd, deps (the script plus the previous output) and outs (metrics for the metrics file).
  • git init → dvc init (creates .dvc/ and .dvcignore) → dvc repro (runs stages and writes dvc.lock).
  • Unchanged stages are skipped; a code change re-runs that stage; new stages run alone. This saves compute during retraining.
  • dvc dag draws the linear pipeline; dvc metrics show prints the metrics.
