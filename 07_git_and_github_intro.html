02Why: a team building a self-driving feature 01:55:11

The instructor's example: you work at Tesla on self-driving cars. Your manager asks your team (he calls it "VGZ16") to add a self-driving feature. You're the team lead, and you split the job: feature 1 to one developer, feature 2 to another, feature 3 to a third.

The complication is that everyone works from somewhere different: one person from home, one from the office, one from their village. Even people who work in the office keep coding at home in their free time. The code still has to end up in one place.

The wrong way

Zip the project and send it around. Nobody knows which zip is newest, changes get overwritten, and there's no history.

  1. You write code and push it to GitHub (think of it as a cloud platform that stores code).
  2. The other developers pull (download) your changes, see what you added (say, feature 0), and build features 1, 2 and 3 on top of it.
  3. They push their work back.
  4. As team lead, you pull, check that every feature was added, finalise, and assign the next piece of work.
  5. Repeat until the project is finished.
Name for this

The instructor calls this cycle code management: sharing, combining and reviewing code across a team through a central remote repository.

03Why: versions must never be lost 01:59:26

No real project reaches production-grade code in one go, a self-driving car included. The instructor shows TensorFlow's release history on PyPI: many versions, each with its own date, released over months and years. When a new version is published, the old ones stay available.

That is what version control means: keep every older version and release new ones on top, instead of replacing code. Git and GitHub do this for your project automatically:

Without version control

v2 overwrites v1. If v2 has bugs, v1 is gone.

With Git + GitHub

v1 stays, and v2 is committed on top of it. Every version remains available, and you don't manage any of it by hand.

This is why Git and GitHub are among the most widely used tools in the software industry.

08Git vocabulary you'll need next

Beyond the video · a glossary for Chapters 08–10
repository (repo)
A project folder whose full history Git tracks.
clone
Download a remote repo, including its full history, to your machine.
commit
A saved snapshot of your changes, with a message. Commits are the "versions".
push / pull
Upload your commits to the remote / download other people's commits.
branch
A separate line of work (for example feature/login) that doesn't affect main until it's merged.
merge
Combine one branch's changes into another.
pull request (PR)
A GitHub request to merge your branch, where teammates review the code first. This is how the "team lead reviews" step works in practice.
fork / star
Your own copy of someone else's repo / a bookmark.
remote (origin)
The name Git uses for the GitHub copy of your repo.

10Interview questions

What's the difference between Git and GitHub?

Git is open-source version-control software that runs locally from the command line and tracks history and branches. GitHub is a Microsoft-owned web platform that hosts remote Git repositories and adds collaboration features: pull requests, code review, issues, Actions for CI/CD, and access control. GitLab and Bitbucket are alternatives to GitHub. Git works without GitHub, but GitHub doesn't work without Git.

Why is version control essential in ML projects?

Several people change the same codebase from different places; you need to roll back when a new version breaks; you must reproduce exactly which code produced a model; and CI/CD pipelines are triggered by commits. For ML specifically, pair Git (code) with DVC (data and models) and MLflow (experiments).

Explain push and pull.

git push uploads your local commits to the remote repository. git pull downloads new commits from the remote and merges them into your local branch (it's a fetch followed by a merge).

Fork vs clone?

A fork is a server-side copy of someone else's repository under your GitHub account, used to contribute to projects you can't push to directly. A clone is a local copy of any repository on your machine. The usual open-source flow is fork → clone your fork → branch → push → open a PR to the original.

A new library version breaks your project. What do you do?

Pin the last working version (for example tensorflow==2.17.0) in requirements.txt, commit it, and rebuild. Longer term, pin all dependencies (a lock file), test upgrades in a branch with CI before merging, and build Docker images from pinned versions so production is reproducible.

How would you use GitHub to show your MLOps skills?

Public repos with modular code, a clear README with an architecture diagram and run instructions, CI workflows (tests, Docker build, deploy), DVC and MLflow configuration, and a link to the live deployed endpoint.

11Recap

  • From now on, all course code lives in GitHub. The series covers the intro, repo setup, commands, and branches.
  • Why (team): developers in different places push to and pull from GitHub, and the team lead pulls, reviews and assigns. This is code management.
  • Why (versions): as with TensorFlow's releases, old versions stay available (install 2.17.0 if 2.18.0 breaks). This is version control.
  • Git = local command-line version-control software. GitHub = Microsoft's web app hosting remote repos, integrated with Git and used by teams.
  • Install Git from git-scm.com on Windows (Mac and Linux usually have it), then sign up at github.com.
  • The feature you'll use most is repositories. Star means like; fork copies a repo into your account.
