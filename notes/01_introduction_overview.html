What MLOps actually is (and what it isn't)

The course opens by fixing a common misconception: MLOps is not just "putting a model into production". It covers the whole life of an ML system: data, code, experiments, deployment, monitoring and retraining. It is learned mostly by using tools.

01Why this course exists

The instructor's opening point: machine learning is not only about building a model. Once a model exists, you still have to answer questions a notebook never asks:

Productionize

How do real users get predictions from it, reliably, 24×7?

Scale

What happens when 10 users become 10,000?

Automate

How do data → training → deployment run without someone doing each step by hand?

The set of tools and practices that answers these questions is MLOps (Machine Learning Operations). The course promises two things:

  1. Learn the MLOps tools needed to productionize an ML system.
  2. Learn to automate the entire ML pipeline with those tools.
Core idea

MLOps = the tools and practices that take an ML model from "works on my laptop" to "runs in production, at scale, and keeps improving automatically".

02The wrong definition vs the right one 01:04

The instructor puts two definitions on the board. The first is the one most people pick up from blogs and YouTube, and he says plainly that it is incomplete.

✗ Common (incomplete) definition

"MLOps is the practice of deploying machine learning models into production."

Why it's wrong: deployment is only one step. It leaves out data, versioning, experiments, automation, monitoring and retraining.

✓ Correct definition (as given in the course)

MLOps refers to the practice and discipline within machine learning that aims to unify and streamline ML system development and ML system operation. It involves collaboration between data scientists, ML engineers and IT professionals to automate and optimize the end-to-end lifecycle of machine learning applications.

The key phrase is "end-to-end lifecycle". That phrase is what makes MLOps "more than deployment", and the analogy chapter spends its whole length explaining what "end-to-end" includes.

03Unpacking the right definition

Here is the definition split into its parts, with what each part means in practice:

Phrase in the definitionWhat it means in practice
"practice and discipline"It is a way of working, not one library. You follow conventions: modular code, versioning, pipelines, CI/CD.
"unify … development and operation"Dev = building the model (data, EDA, features, training). Ops = running it (serving, scaling, monitoring). MLOps joins the two into one flow, the same way DevOps does for software.
"streamline"Remove manual, repeated steps. Anything you do more than once should become a pipeline.
"collaboration between DS, ML engineers, IT"In industry you never build the system alone. Several people work on the same code, data and models, which is why versioning and modular code matter.
"automate and optimize"Pipelines run on their own (automation), and the system keeps improving through experiments and retraining (optimization).
"end-to-end lifecycle"Everything from getting data → training → deployment → monitoring → retraining, then around again. It is a loop, not a straight line.

04ML project vs ML system

The instructor keeps returning to one idea: without MLOps you can still build an ML project, but it breaks when real traffic and changing data arrive. This table summarizes that contrast (it comes up throughout Chapters 02 and 03):

AspectML project (traditional)ML system (with MLOps)
CodeOne Jupyter notebookModular components (ingestion, validation, transformation, trainer, evaluation, prediction)
DataOne CSV fileETL pipelines into a common data warehouse, plus streaming and API sources
VersionsOverwrite and hopeGit/GitHub for code, DVC for data and pipelines
Model choiceOne model, one accuracyMany tracked experiments (MLflow); the best one is promoted
DeployManual: stop server → copy code → restart (downtime)CI/CD + Docker: push to Git and the system updates itself
After deployNobody watches itMonitoring (Grafana, Evidently) detects drift and triggers retraining
ScaleFine for 10–15 usersBuilt for a large audience

06The MLOps Venn diagram: skills you need 00:39:14

The instructor shows the Venn diagram you'll often find online: MLOps sits where three fields overlap.

CIRCLE 1

Machine Learning

Mandatory. Without an ML project, there is nothing to integrate MLOps into. The course assumes you already know the ML lifecycle and does not teach ML from scratch.

CIRCLE 2

Data Engineering

ML is all about data, so you must know how to ingest data from APIs and databases. Big Data is a broad field usually owned by another team, so you don't need it deeply yet.

CIRCLE 3

DevOps

Software concepts (making software scalable, CI/CD, monitoring) come from here. Most MLOps concepts are "taken from DevOps". If you already work in software, you have a head start.

09Interview questions

What is MLOps? Isn't it just deploying models?

No. Deployment is one step. MLOps is the practice of unifying ML development (data, training, evaluation) with ML operations (serving, monitoring, retraining), and automating the whole lifecycle. It depends on collaboration between data scientists, ML engineers and IT/DevOps. A strong answer names the components: data management, versioning, pipelines, experiment tracking, CI/CD, monitoring and retraining.

How is MLOps different from DevOps?

MLOps borrows DevOps ideas (CI/CD, containers, monitoring, infrastructure as code), but ML adds two moving parts that normal software lacks: data and models. Code alone doesn't decide behaviour, so you must also version data (DVC), track experiments (MLflow), and watch for data drift and retrain. In DevOps, a correct release stays correct. In ML, a model can get worse over time even when nobody changes the code.

What skills does an MLOps engineer need?

The Venn diagram gives three: machine learning, data engineering (ingestion, ETL, warehouses) and DevOps (CI/CD, Docker, Kubernetes, cloud, monitoring). You also need Linux, Git and Python OOP for modular code.

Name one tool for each MLOps component.

Data/pipelines: DVC · Versioning: Git/GitHub · Experiments: MLflow · CI/CD: GitHub Actions / Jenkins / CircleCI · Packaging: Docker · Orchestration: Kubernetes · Managed ML: SageMaker · Monitoring: Grafana / Evidently · Scheduling/retraining: Airflow.

10One-minute recap

  • ML is more than model building. You also have to productionize, scale and automate.
  • "MLOps = deploying models" is incomplete. MLOps covers the end-to-end lifecycle, as a loop.
  • It unifies development and operations and relies on collaboration between DS, MLE and IT.
  • MLOps is tool-driven: DVC, Git, MLflow, Docker, CI/CD tools, Kubernetes, SageMaker, Grafana.
  • Prerequisite skills: ML + Data Engineering + DevOps.
