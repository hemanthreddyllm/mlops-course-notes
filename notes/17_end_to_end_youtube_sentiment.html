01The problem, and why classic ML 04:52:34

A creator with a big channel can't read thousands of comments. The project reads them automatically and gives a summary: what share of the audience is positive, neutral and negative. The creator can use that to improve their content.

Problem type

Supervised, multi-class classification. One column holds the comment text and another holds its label: positive, neutral or negative. Three classes make it multi-class; two would make it binary.

Why classic ML, not NLP models or LLMs?

The instructor admits that a transformer (e.g. BERT) or an LLM would give a better-quality model. The point of this chapter is the MLOps workflow (pipeline, tracking, serving), and a text classifier built with classic ML is enough to show it.

Key idea

The problem statement matters less than the workflow: how to analyse data, track experiments, build a pipeline, and serve the model. The same MLOps skeleton works for a deep-learning, NLP or GenAI model.

02The solution: a Chrome extension, and the project plan 04:55:41

Why an extension instead of a website or app? When you open a video, the extension detects that video, fetches its comments and shows a dashboard right away. You don't need to copy links anywhere.

Features the instructor sketches:

  • A summary (e.g. 70% positive, 10% negative, 20% neutral). Percentages are easier to read than counts.
  • Clickable boxes that jump to the positive, negative or neutral comments.
  • A day-by-day graph of sentiment over time.
  • Colour-coded icons next to comments: green for positive, red for negative, blue for neutral.

Heads-up about one statement in the video

While showing the word-count plots, the instructor says the neutral class has more words (the tall peak near zero). A tall peak at a small count means neutral comments are mostly short. The table above confirms it: neutral median = 7 words, versus about 20 for the other classes. The same goes for stop words: neutral comments contain fewer in total, just a higher share of their words.

  • Stop words ("the", "and", "that", …) are about 33% of all words. The instructor counts them per comment, plots them per class, and shows the top 25.
  • Characters and punctuation: new columns with counts, plus a frequency table of special characters (which revealed the Chinese characters).
  • Bigrams / trigrams (CountVectorizer(ngram_range=(2,2)) / (3,3)): "free encyclopedia", "encyclopedia team", "good good"… The instructor admits this step isn't strictly necessary; he added it after seeing it in Kaggle notebooks, and recommends Kaggle notebooks as the best way to learn EDA and feature engineering.

The cleaning function: try it

Every step above ends up in one function, preprocess_comment. The pipeline and the API both call it: training and serving must clean text identically. Two steps matter most:

  • Remove stop words, but keep not, no, but, however, yet. Without them, "I do not like this movie" loses its meaning.
  • Lemmatize (WordNet): plays, played, playing → play. Fewer distinct tokens means fewer dimensions.

    Word clouds: what is this data actually about?

    Beyond the video: what else our EDA found
    • Template or bot text: "free encyclopedia team reached …" and "best overall submitter …" repeat hundreds of times.
    • Repetition spam: "good good good", "movie movie movie".
    • Pre-cleaned text: apostrophes were already stripped ("don", "won"), and no never appears, so two-letter words seem to have been removed before publication.
    • Label noise: some angry comments are labelled positive. The labels look machine-generated, and that noise limits the achievable accuracy.

    05An MLflow server on EC2 with S3 05:33:45

    In Chapter 15, MLflow was hosted on DagsHub. Here the instructor wants a private server (DagsHub repos are public by default) and notes that companies commonly host MLflow on their own cloud.

    1. IAM user mlflow-server: attach policies directly → AdministratorAccess → create. Then Security credentials → Create access key → CLI → download the CSV. (Region: us-east-1, N. Virginia.)

    2. S3 bucket for artifacts, e.g. mlflow-bucket-25. The name must be globally unique; keep the other settings at their defaults.

    3. EC2 instance mlflow-machine: Ubuntu 24.04 LTS, t2.medium (4 GB RAM), a new key pair (required even if you use the browser terminal), allow HTTP/HTTPS, 30 GB storage → Launch → Connect (EC2 Instance Connect).

    4. Install (the commands come from the instructor's MLflow demo repo):

      sudo apt update
sudo apt install python3-pip
sudo apt install pipenv
sudo apt install virtualenv
mkdir mlflow && cd mlflow
pipenv install mlflow
pipenv install awscli
pipenv install boto3
pipenv shell                       # activate the environment
aws configure                      # access key, secret key, us-east-1, default output

    5. Start the server with your bucket name:

      mlflow server -h 0.0.0.0 --default-artifact-root s3://mlflow-bucket-25

    6. Open port 5000: instance → Security → security group → Edit inbound rules → Custom TCP, 5000, 0.0.0.0/0 → Save.

    7. Open the UI at http://<public-IPv4-DNS>:5000. If the browser switches to https://, remove the "s": the server only speaks HTTP.

    8. Test it from Colab: pip install mlflow boto3 awscli, aws configure, then mlflow.set_tracking_uri("http://ec2-…:5000/") and a run that logs a dummy parameter and metric. It appears under the Default experiment.

    Security: don't copy these three shortcuts

    The video uses AdministratorAccess keys, shows them on screen ("I'll delete them after recording"), and opens port 5000 to the whole internet with no login, so anyone who finds the IP can read or delete your runs. For real use:

    • Give the instance an IAM role limited to that bucket.
    • Allow port 5000 from your IP only, or put the server behind nginx with authentication or MLflow's basic-auth app.
    • Use HTTPS.

    Also, the run metadata lives on the instance's disk, so terminating the instance loses every run. The instructor actually hit this: he terminated the server between recording days and had to start a new one. For a durable server, point --backend-store-uri at a database such as RDS PostgreSQL.

    06Experiment 1: the baseline 05:48:52

    The notebook applies the same cleaning function to the whole dataset and then:

    1. CountVectorizer(max_features=10000) (bag of words) → X has shape (36k, 10000).
    2. mlflow.set_tracking_uri(...) and mlflow.set_experiment("RF Baseline"). A dedicated experiment is used instead of Default.
    3. aws configure in Colab, so artifacts can reach S3.
    4. An 80/20 stratified split, then a with mlflow.start_run(): block that:
      • sets tags and a description
      • logs params (vectorizer_type, max_features, and n_estimators and max_depth for the Random Forest)
      • trains, predicts, and logs accuracy plus per-class precision, recall and F1 from classification_report
      • logs a confusion-matrix heatmap, the model and the dataset as artifacts

    Result in the video: 64% accuracy, with high precision but poor recall on the minority classes, which points to imbalance. The cleaned data is then saved as reddit_preprocessing.csv, so later notebooks don't repeat the preprocessing. In S3, each run's artifacts sit under <experiment_id>/<run_id>/.

    07Experiments 2–3: vectorizer, n-grams, feature count 05:57:18

    Bag of words (CountVectorizer)

    Raw counts of each term. ngram_range=(1,1) is unigrams; (1,2) adds bigrams (two-word tokens); (1,3) adds trigrams.

    TF-IDF (TfidfVectorizer)

    Counts are down-weighted for terms that appear in many documents, so rarer, more specific terms stand out. (Word2Vec was mentioned but not tried.)

    Experiment 2 ("Exp 2 – BoW vs TfIdf") is a loop over 2 vectorizers × 3 n-gram settings with 5,000 features: 6 runs. In the MLflow UI: select all → Compare → parallel coordinates plot, then switch the metric.

    Metric chosen in the plot (video)Winner
    accuracyBoW + bigrams (≈ 65%)
    negative-class precisionBoW + bigrams
    negative-class recall (the deciding metric)TF-IDF + trigrams ✔

    Why recall? Because of the imbalance, precision on the minority class looks good while many negatives are still missed. Recall tells you how many of the real negatives you catch.

    Experiment 3 ("Exp 3 – TfIdf Trigram max_features") fixes TF-IDF (1,3) and loops max_features over 1000, 2000, …, 10000: 10 runs. In the video, accuracy rises as features decrease, negative precision is higher with more features, and negative recall is best at 1000. Conclusion: 1000 features (fewer features, higher recall).

    08Experiment 4: class imbalance 06:12:15

    With TF-IDF (1,3) and 1000 features fixed, the notebook tries five techniques in a loop (resampling only the training split):

    TechniqueHow it worksIn the video's comparison
    class_weight="balanced"mistakes on rare classes cost more; the data is unchanged–
    Oversampling (SMOTE)creates synthetic minority rows by interpolating between neighboursbest overall once positive precision and recall are also compared ✔

    Settings after four experiments

    TF-IDF · trigrams (1,3) · max_features=1000 · SMOTE oversampling. Every later model is trained with these settings. The instructor's summary also mentions the baseline's 64%, the starting point these settings improve on.

    09Experiments 5–6: algorithms, tuning, stacking 06:18:36

    With the settings fixed, the instructor trains several classifiers (XGBoost, decision tree, KNN, naive Bayes, LightGBM…), each with Optuna hyperparameter tuning. Each model has its own notebook, because tuning them all in one notebook takes too long. He shows two:

    • XGBoost (30 Optuna trials): XGBoost needs labels 0…n−1, so −1 is remapped to 2 (0 = neutral, 1 = positive, 2 = negative).
    • LightGBM, the winner, then tuned in detail (100 trials). That produced the pipeline's parameters: learning_rate=0.09, max_depth=20, n_estimators=367.

    He says Optuna is more powerful than GridSearchCV and encourages you to try other models: "only the model changes; the rest of the code stays the same."

    Stacking combines several models: base learners logistic regression + KNN + LightGBM, and a meta-learner on top (StackingClassifier). The result was about the same as LightGBM alone, so the instructor kept the simpler LightGBM. A stack is a more complex architecture to run and maintain.

    How our re-run differs

    Our 2_experiments.ipynb puts all six rounds in one notebook with fewer Optuna trials, so it finishes in minutes. It fits vectorizers on the training split only, and tunes on a validation split carved from training data. The best configuration then gets one test-set score. Absolute numbers differ from the video's, but the conclusions are what matter.

    10The DVC pipeline and the model registry 06:26:00

    The notebook code is rewritten as modular Python files, chained with dvc.yaml. The components:

    Project set-up 06:29:13

    • Create the GitHub repo YouTube-Sentiment-Insights (README, Python .gitignore, MIT licence) → git clone → open it in VS Code.
    • Folders: notebooks/ (the Colab notebooks, for reference), data/ (pipeline outputs), src/data/ and src/model/ with an __init__.py so src is a local package, plus dvc.yaml, params.yaml, requirements.txt and setup.py.
    • conda create -n youtube python=3.11 → pip install -r requirements.txt. Its last line, -e ., installs src via setup.py, which creates the *.egg-info folder.
    • dvc init (git must already be initialised, which the clone provides).
    • Add data/ to .gitignore → git add . && git commit && git push origin main.

    Each component, built and tested one at a time

    The instructor adds one stage to dvc.yaml at a time and runs dvc repro after each. Stages that already ran are skipped ("didn't change, skipping"), so each new run starts at the newest stage. Every module follows the same pattern: a logger, load_params(), load_data(), the step itself, save_…(), and a main() wrapped in try/except.

    The back end sits between the extension and the model. It receives comments, preprocesses them with the same function, vectorizes them with the saved TF-IDF object (raw text must become numbers the same way as in training), predicts, and returns the result.

    RouteInput (JSON)Output

    Deployment plan, carried out in Chapter 18:

    1. Log in to the AWS console and create an IAM user with the required policies.
    2. Build the Docker image of the source code and push it to ECR (Elastic Container Registry, AWS's alternative to Docker Hub).
    3. Launch an EC2 virtual machine.
    4. Pull the image from ECR onto EC2 and run it.
    5. Map the port, then open the app.

    The automation lives in .github/workflows/cicd.yaml (the folder structure must be exact), run by GitHub Actions. The instructor adapted a standard "GitHub Actions + AWS" template. It does continuous integration, delivery and deployment, and exposes the app on port 8080. Chapter 18 explains CI/CD from scratch.

    Port numbers get mixed up

    The API runs on 5000 locally (Flask's default). The container and the CI/CD file use 8080; the video says "8080" and then "port number 8000" in the same sentence, and 8080 is the right one. Whatever you choose, the Flask or gunicorn port, -p host:container, the security-group rule and API_URL in popup.js must all match. On macOS, port 5000 is taken by AirPlay Receiver, so our local API uses 5001.

    14Precision notes

    • "$300 free credits" on a new AWS account: $300 is Google Cloud's trial amount. AWS's current free tier (since July 2025) gives new accounts up to $200 in credits. Either way, set a billing alarm.
    • Data leakage in two course notebooks. The baseline fits CountVectorizer on all rows before splitting. The LightGBM tuning notebook applies SMOTE to the whole dataset before splitting, so the test set contains synthetic rows made from training rows, and its accuracy is optimistic. Notebooks 2–5 do it correctly: fit and resample on train only.
    • Tuning on the test set. The Optuna objectives score each trial on the test split, and the best trial is reported on that same split. Use a validation split or cross-validation for tuning, and keep the test set for one final check.
    • Picking the metric. "Negative recall" was the stated criterion, but experiment 4's final pick weighed several metrics by eye. In practice, decide one primary metric before the experiments (e.g. macro-F1 or negative-class recall at a minimum precision).
    • SMOTE on text interpolates between TF-IDF vectors. It works, but the synthetic "documents" aren't real text. class_weight is simpler and often as good, especially for boosted trees (e.g. class_weight="balanced" in LightGBM).
    • MLflow stages are deprecated (MLflow 2.9+): transition_model_version_stage and get_latest_versions(stages=…). Use aliases. In MLflow 3, mlflow.sklearn.log_model saves in skops format, which refuses to load LightGBM classes. Log the model with mlflow.lightgbm.log_model instead (we hit this).
    • app.run(host="0.0.0.0", debug=True) in the course API: the Werkzeug debugger allows running code from the browser, so never expose it on a network. Use gunicorn or uWSGI in production. Flask's server is for development only.
    • The course repo's popup.js contains a real-looking API key. Anything in extension JavaScript is readable by every user. Restrict the key in GCP (to the YouTube Data API only), rotate it if it leaks, or have the back end call YouTube so the key never ships to the browser.
    • Dockerfile: python:3.8-slim-buster is doubly end-of-life (Python 3.8 in Oct 2024, Debian buster in June 2024). COPY . /app without a .dockerignore also copies data, notebooks, .git and any local secrets into the image. The course README itself says to use Python 3.11.
    • Model loaded from a local pickle. That skips the registry, so there's no guarantee the API serves the registered version. Load by alias (@staging / @production) or bake the exact registered version into the image in CI.
    • "Chrome plug-in": Chrome calls these extensions. (NPAPI plug-ins were removed from Chrome in 2015.) New extensions must use Manifest V3.
    • Domain shift. The model learned from (mostly Indian political) Reddit comments, and the extension applies it to any YouTube video. Expect worse results on tech or entertainment comments, and on short, sarcastic or emoji-only comments. Monitoring and retraining with real YouTube data would be the next MLOps step.
    • register_model has side effects that DVC doesn't track. Re-running the stage creates a new registry version even when the model is identical. Our walkthrough shows this happening.

    Walk me through an end-to-end ML project you built.

    Use this project as the answer: problem (summarise YouTube comment sentiment) → data (a labelled Reddit set, imbalanced) → EDA and a single shared cleaning function → experiments tracked on a self-hosted MLflow server (baseline → vectorizer and n-grams → feature count → imbalance → model selection with Optuna → stacking rejected for complexity) → DVC pipeline with params.yaml → evaluation logged to MLflow → registry alias → Flask API → Chrome extension client → Docker → GitHub Actions to ECR/EC2. Mention the weaknesses too (domain shift, label noise) and what you'd add next (monitoring, retraining on real YouTube data).

    Why save the TF-IDF vectorizer, and why must preprocessing be shared?

    The model only understands the feature space it was trained on. The API has to turn new text into exactly the same columns, with the same vocabulary and IDF weights, so it loads the fitted vectorizer rather than fitting a new one. The cleaning function must also be identical, or you get training/serving skew: the model sees differently-cleaned text in production and quietly gets worse. Putting both in one shared module (or one sklearn Pipeline object) prevents that.

    Your classes are 43 / 35 / 22%. How do you evaluate and handle that?

    Look at per-class precision and recall, macro-F1 and the confusion matrix, not just accuracy. Options: class_weight, oversampling (SMOTE or ADASYN), undersampling, or hybrids such as SMOTEENN. Apply them to the training data only, after the split (inside CV folds when cross-validating). Adjusting decision thresholds per class also helps.

    Bag of words vs TF-IDF vs embeddings?

    BoW gives sparse counts; common words dominate. TF-IDF also gives sparse vectors, but down-weights terms that appear everywhere, which is usually better for linear and tree models. N-grams capture short phrases like "not good". Embeddings (Word2Vec, sentence transformers) are dense and capture meaning, handle synonyms, and generalise better, but cost more to compute. Transformers fine-tuned on the task usually do best on sentiment.

    How did you choose between LightGBM and a stacking ensemble?

    Their scores were about the same, so the simpler model wins: it's faster to train and serve, has fewer components to break, is easier to explain, and is easier to retrain. An ensemble earns its complexity only with a clear, significant gain on held-out data.

    How do you host MLflow for a team?

    mlflow server on a VM or container, with:

    • a database backend store (e.g. PostgreSQL on RDS)
    • an object-store artifact root (S3), or --artifacts-destination to proxy uploads through the server
    • IAM roles instead of static keys
    • HTTPS and authentication, or a private network
    • backups

    Alternatives are managed services: Databricks, SageMaker MLflow, DagsHub.

    What does dvc repro do when you change only n_estimators?

    DVC hashes each stage's deps and params. Only model_building declares model_building.* params, so ingestion and preprocessing are skipped. Building re-runs, and evaluation and registration re-run because their input changed. If you revert the param, DVC's run-cache restores the earlier outputs without retraining. Stages with external side effects, like registration, still re-run.

    How would you promote a model from staging to production safely?
    • Automated checks on the candidate: metrics above thresholds and no worse than production on a fixed test set, the signature and schema unchanged, a latency budget met, and API contract tests passing.
    • Then move the @production alias (or stage), roll out gradually (canary or shadow), monitor, and keep the previous version for instant rollback.

    The course repo sketches this in scripts/ (test_model_performance.py, promote_model.py).

    The extension works for you but not after deployment. What do you check?
    • API_URL in popup.js points to the server.
    • host_permissions in the manifest includes that URL.
    • CORS is enabled on the API.
    • The security group allows the port.
    • The container publishes the right port (-p 8080:8080) and the app binds to 0.0.0.0.
    • HTTPS vs HTTP: mixed content, and Chrome's Private Network Access rules.
    • The container logs.
    • The YouTube API key's quota and restrictions.

    16Recap

    • Problem → solution: summarise YouTube comment sentiment with a Chrome extension (front end) and a Flask API (back end).
    • Data: Reddit comments labelled 1 / 0 / −1, about 43 / 35 / 22% (imbalanced) and mostly political.
    • Cleaning: drop missing values, duplicates and blanks; lowercase; strip; remove \n and special characters; remove stop words but keep negations; lemmatize. One shared function does it all.
    • MLflow on EC2: IAM keys, an S3 artifact bucket, a t2.medium Ubuntu instance, pipenv installs, mlflow server -h 0.0.0.0 --default-artifact-root s3://…, and port 5000 opened. (Secure it properly.)
    • Experiments: baseline (64%) → TF-IDF (1,3) → 1000 features → SMOTE → LightGBM (tuned with Optuna) → stacking gives no gain, so LightGBM stays.
    • Pipeline: ingestion → preprocessing → building → evaluation (MLflow, experiment_info.json) → registration (Staging, or an alias in MLflow 3), driven by dvc.yaml and params.yaml.
    • Serving: Flask routes for prediction and charts, tested in Postman. The extension needs a YouTube Data API key and is loaded with "Load unpacked". Change API_URL before deploying.
