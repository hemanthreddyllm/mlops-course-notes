ML pipelines, and why they need tracking

The course now moves from code to ML pipelines. The instructor explains what a pipeline is (ordered steps from data ingestion to deployment), why production pipelines get re-run for retraining, and why re-running steps whose inputs haven't changed wastes compute. DVC (Data Version Control) is the tool the course uses to build pipelines and track them, so each stage runs only when something it depends on has changed.

01What DVC is, and what this series covers 02:25:54

DVC = Data Version Control. It does two things:

CAPABILITY 1

Data versioning

Version large datasets and model files, the way Git versions code. Not the focus here. The instructor treats data management as a big-data topic that a separate team usually owns.

CAPABILITY 2 · THIS SERIES

ML pipelines and pipeline tracking

Define the pipeline's stages, run them in order, and track them so unchanged stages are skipped.

What an MLOps engineer needs to know about data

You don't need to own data management, but you should be able to ingest data from a database, an API or a website into your pipeline.

The series has two parts: this introduction (what DVC is and why it's needed), then a demo that builds a pipeline and tracks it with DVC.

02Why DVC and not Kubeflow or Airflow? 02:26:57

Kubeflow and Airflow can also build and track pipelines. The instructor chose DVC for these reasons:

  • Easy to set up. It installs with pip and needs very little configuration. Kubeflow and Airflow take much more setup and often throw errors along the way.
  • Popular and used in production. He first used it when it was closer to a proof-of-concept tool. Today it's used in production and has grown from classic ML to deep learning and GenAI workflows.
  • Transferable skills. MLOps has "thousands of tools", and nobody learns them all. Once you understand one pipeline tool well, the others are much quicker to pick up.

03What an ML pipeline is 02:30:08

Every end-to-end ML or deep learning project follows a fixed order of execution. The instructor points to the end-to-end projects on his YouTube channel, which all share this outline: project introduction → GitHub repo setup → template creation → workflow → notebook experiments → the pipeline → app → Dockerisation → deployment.

The instructor's example: the dataset should have 5 features, but after ingestion only 4 arrive. Validation catches the missing column, and the pipeline does not continue to training.

05Retraining: why pipelines get re-run 02:34:21

In production, pipelines aren't run just once. The model may start performing poorly, or the data may change. The instructor's example:

TODAY

500 rows

Train the model on this dataset.

3 MONTHS LATER

1,000 rows

Run the whole pipeline again (ingestion → validation → transformation → training → evaluation → prediction). That's retraining.

Production should be automated, just like the cooking business in Chapter 02 ended up automated. So you can schedule retraining, for example every 2 or 3 months, and let it start on its own.

06Why tracking matters: skip what hasn't changed 02:35:25

The problem with blind scheduled retraining

If the data hasn't changed (and the code hasn't either), retraining produces the same model. That's unnecessary computation in the cloud, and you pay for it.

So you need to track two things:

  • Has the data source changed?
  • Has the code changed, for example a new feature added?

Rerun only when one of them has changed, and do the check automatically rather than by hand. That's what DVC does.

07How DVC decides what to run 02:36:29

DVC automates the "did anything change?" check for every stage. It requires Git, so the project must be a Git repo.

08Installing DVC and reading the docs 02:28:00

  • The official site is dvc.org, with full documentation, install guides for each OS, and tutorials.
  • Install with pip: pip install dvc, or list dvc in requirements.txt.
  • The instructor's advice: watch his demo first, then read the documentation. The docs are always up to date when new versions and features come out.
Beyond the video · remote-storage extras

To push versioned data and models to cloud storage, install the matching extra: pip install "dvc[s3]" (AWS), "dvc[gs]" (GCP) or "dvc[azure]". Check the install with dvc version.

09Interview questions

What is DVC and why use it alongside Git?

DVC is an open-source tool that adds versioning for data and models, plus reproducible pipelines, to a Git repo. Git can't handle large binary files well, so DVC stores them in a cache or remote storage (S3, GCS…) and commits small pointer files, the pipeline definition (dvc.yaml) and the lock file (dvc.lock) to Git. A Git commit then pins code, data and model versions together.

What are the typical stages of an ML training pipeline?

Data ingestion → data validation → data transformation / feature engineering → model training → model evaluation (often followed by a model registration or "pusher" step). Serving adds a prediction pipeline, an app or API, and deployment.

Why track a pipeline instead of just re-running a script?

For reproducibility (you know exactly which inputs produced which outputs) and efficiency (only stages with changed code, data or parameters re-run). That matters a lot when training is expensive and retraining is scheduled.

When should a model be retrained?

When new data arrives, when monitoring shows data drift or a performance drop, or when code or features change. Scheduled retraining is common, but pair it with change detection or drift checks so you don't retrain on identical inputs.

What does data validation check, and what happens when it fails?

It checks the schema (columns, types), missing values, value ranges and distribution drift against a reference. On failure the pipeline stops before training, raises an error or alert, and saves a validation report, so a broken dataset never produces a production model.

DVC vs Airflow vs Kubeflow?

DVC: lightweight, built on Git, reproducible pipelines with automatic skipping of unchanged stages, plus data versioning, but no scheduler of its own. Airflow: a general workflow orchestrator with scheduling, retries and a UI, suited to ETL. Kubeflow Pipelines: ML pipelines on Kubernetes with step caching, suited to large platforms. They're often combined, for example Airflow or CI triggering dvc repro.

10Recap

  • DVC = Data Version Control. It versions data and builds and tracks ML pipelines; this series uses the pipeline part.
  • Chosen over Kubeflow and Airflow because it's easy to set up, popular and used in production. Learn one pipeline tool and the others come easily.
  • Pipeline: ingestion → validation → transformation → training → evaluation → prediction → app → deployment, each stage depending on the previous one.
  • Validation is a gate: expected 5 features, got 4 → stop.
  • Retraining re-runs the pipeline when data grows (500 → 1,000 rows), often on a schedule.
  • Retraining unchanged inputs wastes compute, so track changes to data and code. DVC does this automatically, and it needs Git.
