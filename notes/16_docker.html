01Why Docker? "It works on my machine" 04:05:18

The official definition: Docker is a platform designed to help developers build, share and run container applications. Two everyday problems explain why it exists:

Problem 1 · Deploying

You build on your laptop, then move the project to a cloud VM (e.g. an Ubuntu EC2 instance) and install the packages there. It throws errors because some specific package version isn't satisfied in that environment.

Problem 2 · Sharing

A teammate or tester has to recreate your environment and install everything, and they hit the same version problems.

Docker's answer

Build an image of your entire source code and its environment, then run that image on a Docker engine, which creates a container. The same image runs the same way on a cloud server, a Mac or any other developer's machine. The only requirement is that the machine has a Docker engine running.

04The components of Docker 04:12:38

① Docker Engine (container engine)

The core of Docker. It creates, runs and manages containers, and is the runtime behind Docker's containerisation.

② Docker image

A lightweight, standalone, executable package containing everything the software needs to run: code, runtime, libraries, environment variables and configuration files. Containers are created from images.

COMPONENT

Base image

The starting point, usually a minimal OS such as Alpine (a small Linux) or Ubuntu, often with a language runtime such as Python already installed.

COMPONENT

Application code

Your project files.

COMPONENT

Dependencies

Libraries from requirements.txt and similar.

COMPONENT

Metadata

Exposed port, start command, labels, environment.

Image lifecycle: create → store (locally or in a registry) → distribute → someone pulls and executes it.

③ Dockerfile

A text file with a series of instructions for building an image. Each instruction creates a layer, and layers are cached and reused, which makes rebuilds efficient. Instructions are written layer by layer in order, not randomly, and Dockerfiles automate image creation in a consistent, reproducible way. (Walkthrough in section 12.)

④ Docker container

A lightweight, portable, isolated environment that wraps an application and its dependencies so it runs the same across environments. Containers are instances of images, and images themselves are immutable.

The DVD analogy

An image is like a music DVD. Play it on a computer or on a smart TV, and each player becomes the "container" running that same content. Run a Python image and you get a running Python container.

⑤ Docker registry

A service that stores and distributes images. You can publish your own images and tag versions (e.g. v1, latest) so users can tell which one is newest.

08Installation 04:25:32

Linux and macOS are straightforward: follow Install Docker Engine on docs.docker.com (the Ubuntu page lists every command), or install Docker Desktop on a Mac. Windows needs a few extra steps, because Docker runs on Linux:

  1. Download Docker Desktop for Windows (search "docker install windows").

  2. Install the WSL 2 update package (the instructor shares the installer in the course resources).

  3. Open Turn Windows features on or off and enable Virtual Machine Platform and Windows Subsystem for Linux, then restart.

  4. From the Microsoft Store, install Ubuntu (the latest version), open it, and create a username and password. A Linux kernel is now running on Windows.

  5. Run the Docker Desktop installer (Next, Next…), then open Docker Desktop and wait for the engine to be running. The first start can take 10–15 minutes.

  6. Settings → Resources → WSL integration: enable your Ubuntu distro.

  7. Verify in a terminal: docker --version should print a version, and docker ps should print an empty table. An error means the install didn't finish.

Beyond the video · your Mac

Install Docker Desktop for Mac, picking the Apple-silicon or Intel build to match your chip. Lighter alternatives are Colima and OrbStack. On a work laptop, note that Docker Desktop needs a paid subscription at larger companies. Docker Engine on a Linux server (such as EC2) is free.

09Practical demo: hello-world 04:30:14

  1. Docker Desktop is empty at first: no containers, no images. Sign in with a Docker Hub account (create one at hub.docker.com, e.g. with Gmail).
  2. Docker Hub → Explore shows images for TensorFlow, PyTorch, LangChain, NGINX, BusyBox, Alpine, Grafana and more. Search python and you'll find many version tags.
  3. Open the hello-world image, copy its pull command, and run it:
terminal
$ docker pull hello-world          # downloads layer by layer (only if not already local)
$ docker images                     # REPOSITORY  TAG  IMAGE ID  …  → hello-world
$ docker run hello-world
Hello from Docker!
This message shows that your installation appears to be working correctly.
$ docker ps -a                      # the container, with a random name, status "Exited"
$ docker rm <container-id>          # delete the container (ID from ps -a)
$ docker rmi hello-world            # delete the image
$ docker pull hello-world           # pull it again: image present, no container yet

Each docker run creates a new container with a random name (the instructor's was "happy_summit"). hello-world prints its message and exits, so it isn't "running" afterwards. On a cloud server there's no Docker Desktop, so learn the terminal commands.

11Custom image: the calculator app 04:37:43

The instructor containerises a simple Flask calculator: two numbers, then add, subtract, multiply or divide, with an HTML template and a CSS file. The app doesn't matter: the same steps work for any ML or DL project. What you need to learn is how to write the Dockerfile, build the image, run it, and push it.

  1. Activate the environment and pip install -r requirements.txt. The instructor points out that these exact pinned versions are what might break on an Ubuntu server, which is the reason to containerise.
  2. python app.py, then open localhost:8080 and try an addition (23 + 4…). It works.
  3. Create a file named Dockerfile (capital D, no extension).

12The Dockerfile, line by line 04:40:52

The instructor's Dockerfile. Click a line.

Beyond the video · the improved version used in the hands-on project 
FROM python:3.11-slim                     # maintained Debian base (buster is end-of-life)
WORKDIR /app
COPY requirements.txt .                   # dependencies first → cached layer
RUN pip install --no-cache-dir -r requirements.txt
COPY . .                                  # code changes don't re-install packages
EXPOSE 8080
CMD ["gunicorn", "--bind", "0.0.0.0:8080", "--workers", "2", "app:app"]   # production server

Plus a .dockerignore (__pycache__/, .venv/, .git/, .env…) so junk and secrets never get copied into the image.

13Build, run, detach, push, pull 04:42:58

the video's sequence
$ docker build -t entbappy/mycalapp:latest .     # pulls the base, installs deps, bakes the image
$ docker images                                  # the new image appears (also in Docker Desktop)
$ docker run -p 8080:8080 entbappy/mycalapp:latest
  → allow the firewall prompt on Windows; open localhost:8080 → the calculator now runs FROM THE CONTAINER
$ docker ps                                      # (second terminal) the container is Up
  Ctrl+C in the first terminal → the container stops too
$ docker run -d -p 8080:8080 entbappy/mycalapp:latest   # detached: keeps running
$ docker stop <id>                               # or the Stop button in Docker Desktop
$ docker login                                   # authenticate to Docker Hub
$ docker push entbappy/mycalapp:latest           # now listed under your Docker Hub repositories
  … anyone can find it on Docker Hub (the instructor checks in an incognito window) …
$ docker rm -f $(docker ps -aq)                  # remove all containers (then the local image)
$ docker pull entbappy/mycalapp:latest           # download it back from the Hub
$ docker run -p 8080:8080 entbappy/mycalapp:latest   # works exactly the same
Why this matters for the rest of the course

Every CI/CD deployment follows this pattern: containerise the app → build the image → run it on a server. Docker has more (Compose, volumes…), but the instructor covers only what the course's projects use. His homework: containerise any project of your own, push it to Docker Hub, and run it.

14Precision notes

Things to fix or know when you copy the video's setup
  • python:3.11-slim-buster is outdated. Debian 10 "buster" is end-of-life, so use python:3.11-slim (current Debian). Also, slim images are Debian-based, not Alpine. Alpine variants are named -alpine.
  • Copy requirements.txt before the code. With COPY . /app first, any code change invalidates the cache and reinstalls every package on each build.
  • The Flask development server isn't for production. The course's requirements already include gunicorn. Use it as the CMD. Also bind to 0.0.0.0, not 127.0.0.1, or the app is unreachable from outside the container.
  • Old pins. The course app pins Flask==1.1.2 / Jinja2==2.11.2 (2020), which have known vulnerabilities and don't install cleanly on new Pythons. The hands-on project uses Flask 3.1.
  • Isolation isn't a resource limit. Containers isolate processes and files, but a busy container can still use all the CPU and RAM unless you set --memory / --cpus (or Kubernetes limits).
  • Ctrl+C stopped the container because it was running attached in the foreground. With -d it keeps running until docker stop.
  • Docker Hub isn't only public: it offers private repositories too. Google Container Registry has been replaced by Artifact Registry.
  • Apple-silicon Macs build arm64 images. An x86 EC2 server needs docker build --platform linux/amd64 … (or a multi-arch build with docker buildx), otherwise you get exec format error.

15Interview questions

Image vs container?

An image is an immutable, layered template (filesystem plus metadata). A container is a running, or stopped, instance of an image with its own writable layer, process space and network. One image can back many containers.

Container vs virtual machine?

A VM virtualises hardware and runs a full guest OS on a hypervisor: strong isolation, but GBs in size and minutes to boot. A container shares the host OS kernel and isolates processes with namespaces and cgroups: MBs, starts in seconds, higher density, but weaker isolation than a VM.

How does Docker layer caching work, and how do you use it well?

Each instruction produces a layer. On rebuild, Docker reuses cached layers until one changes, and everything after that is rebuilt. So order instructions from least to most frequently changing: base image → system packages → COPY requirements.txt + pip install → COPY the code.

CMD vs ENTRYPOINT? COPY vs ADD? EXPOSE vs -p?

ENTRYPOINT sets the executable. CMD gives default arguments (or the default command) and is easily overridden at docker run. COPY copies local files. ADD can also fetch URLs and extract tar files, so prefer COPY for clarity. EXPOSE only documents a port. -p host:container actually publishes it.

How do you keep an ML image small and secure?

Use slim bases, --no-cache-dir, a .dockerignore, and multi-stage builds (compile or train in one stage, copy only the artefacts into the runtime stage). Pin versions, run as a non-root user, never bake secrets in (pass them as env vars or secrets at runtime), scan images (e.g. docker scout, Trivy), and keep large models out of the image when possible (pull them from S3 or a registry at start-up).

How do you persist data or debug a running container?

Persist with volumes (-v name:/path) or bind mounts, since a container's own writable layer disappears with it. Debug with docker logs -f, docker exec -it <name> sh, docker inspect and docker stats.

What is Docker Compose?

A YAML file describing a multi-container app (e.g. an API, a database and an MLflow server) with networks, volumes and environment variables, started with docker compose up. It's great for local stacks. Kubernetes (Chapter 21) orchestrates containers across a cluster.

Your image runs on your Mac but fails on EC2 with "exec format error". Why?

An architecture mismatch: the image was built for arm64 (Apple silicon) and the server is amd64. Rebuild with --platform linux/amd64, or publish a multi-arch image with docker buildx build --platform linux/amd64,linux/arm64 --push.

16Recap

  • Docker solves "works on my machine": package the app and its environment as an image, run it as a container on any Docker engine. (Maggi masala packet = image.)
  • Benefits: consistency across dev, test and prod, and isolation between apps on one host.
  • Components: Engine (CLI → REST API → daemon), image (base + code + deps + metadata), Dockerfile (instructions = layers), container (an image instance), registry (Docker Hub, ECR, GCR/Artifact Registry, ACR, with tags).
  • Install: Docker Desktop. On Windows, add WSL 2, enable the VM Platform and WSL features, install Ubuntu, and turn on WSL integration. Verify with docker --version and docker ps.
  • Demo: pull, images, run, ps -a, rm, rmi with hello-world.
  • Custom image: Dockerfile (FROM, WORKDIR, COPY, RUN, EXPOSE, CMD) → docker build -t user/app:tag . → docker run -p 8080:8080 (add -d for background) → docker login / push → anyone can pull and run.
