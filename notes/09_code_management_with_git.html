01Why not just zip the code? 02:13:16

The instructor creates test.py with a simple print, which stands in for version 1 of a project with feature 1 added. The code exists only on his machine. To share it the old way, he'd zip it and upload it to Google Drive, and with 100 developers each of them would have to download and open it. That's tedious and error-prone.

Instead

Commit the code from your machine and push it to the GitHub server. Everyone else just pulls. Four commands make this work.

02The four places your code lives

04Step 2: git add (staging) 02:15:25

Before pushing, you add files to the staging area (the auto-captions say "stressing area"). You can stage one file by name or everything with .. The instructor creates a second file, test2.py, to show the difference:

~/github-learning-test (main)
$ git status
Untracked files:
        test.py
        test2.py
$ git add test.py              # stage only this one
$ git status
Changes to be committed:
        new file:   test.py
Untracked files:
        test2.py                 # not staged, so it won't be in the commit

git add <file>

Stage specific files. Useful when you only want some of your changes in this commit.

git add .

Stage everything that changed in the current folder, except files matched by .gitignore.

Why a staging area?

It lets you build a commit deliberately. For example, you might commit a bug fix now and keep an unfinished experiment out of it. Undo staging with git restore --staged <file>. Check what's staged with git diff --staged.

05Step 3: git commit 02:16:29

A commit finalises the staged changes as a saved version. -m attaches a message describing the change.

~/github-learning-test (main)
$ git commit -m "test.py file added"
[main 3f9c2a1] test.py file added
 1 file changed, 1 insertion(+)
 create mode 100644 test.py
$ git status
Untracked files:
        test2.py                 # test.py no longer listed: it's committed

After the commit, test.py disappears from git status. From now on Git tracks it: any later edit makes it show up as modified.

Writing good commit messages

Use the imperative mood and say what changed and why: Add data ingestion component, Fix NaN handling in feature scaler. Avoid update or changes. In MLOps, CI tools and MLflow runs show these messages, so clear ones make a model's history readable.

origin

The name git clone gave to the GitHub copy of the repo (the remote).

The branch you're pushing. GitHub creates main by default, and the terminal prompt shows which branch you're on.

Refresh the repo page on GitHub and test.py is there with its code. Other developers can now see it and pull it.

07git pull, and a second developer's change 02:18:35

~/github-learning-test (main)
$ git pull
Already up to date.          # the instructor already has everything

A teammate who runs git pull receives test.py. The instructor then acts as that teammate: he adds feature 2 to test.py and runs the same cycle again.

~/github-learning-test (main) · "developer 2"
$ git status
Changes not staged for commit:
        modified:   test.py
$ git add test.py
$ git commit -m "test.py file updated"
$ git push origin main          # GitHub now shows feature 2
Rule of thumb

Pull before you start work, and pull before you push. If someone pushed in the meantime, your push is rejected ("fetch first") until you pull and combine their commits with yours. When two people changed the same lines, Git asks you to resolve a merge conflict (covered in Chapter 10).

09Going back to a previous version 02:19:37

Suppose the updated version (feature 2) has a bug and the previous version worked. Because every commit is saved, you can find the old code:

  1. On the GitHub repo page, open the commit history (the clock icon with the commit count).
  2. Click the older commit, "test.py file added", to see exactly what changed in it (view commit details).
  3. Click "Browse the repository at this point" (the <> icon) to see all files as they were then, including the old test.py.

Each commit has a unique commit ID, a hash such as 3f9c2a1… (40 hex characters, usually shown shortened to 7).

Correction

The video suggests that after browsing the old commit on GitHub you can "simply do git pull" to get the previous code back. git pull only brings down the latest commits. It never restores an old version. Use one of the commands below.

~/github-learning-test (main)
$ git log --oneline              # find the commit IDs
c07fa55 (HEAD -> main, origin/main) files added
8d41e07 test.py file updated
3f9c2a1 test.py file added
a1b2c3d Initial commit
$ git show 3f9c2a1:test.py       # just LOOK at the old file
$ git restore --source 3f9c2a1 test.py   # bring the old file back into your working dir
$ git revert 8d41e07             # or: add a NEW commit that undoes the buggy one
$ git push origin main           # share the fix
GoalCommandSafe on a shared branch?
View an old versiongit show <id>:file · git switch --detach <id>✓ read-only
Restore one filegit restore --source <id> file, then commit✓
Undo a commit that's already pushedgit revert <id>✓ keeps history, adds an "undo" commit
Throw away local commitsgit reset --hard <id>✗ rewrites history; only for work nobody else has

10Committing everything with git add . 02:20:41

To finish, the instructor creates test3.py and commits all pending files together:

~/github-learning-test (main)
$ git add .                       # test2.py + test3.py
$ git commit -m "files added"
$ git push origin main            # refresh GitHub: both files appear
The loop you'll repeat constantly

git status → git add . → git commit -m "message" → git push origin main, and git pull to get teammates' work. This is version control and code management with Git and GitHub.

12Interview questions

Explain the working directory, the staging area and the repository.

The working directory holds the files you edit. The staging area (index) holds the snapshot you've selected for the next commit, filled with git add. The local repository (.git) stores the commits you've made with git commit. The remote (GitHub) receives them with git push.

git fetch vs git pull?

fetch downloads new commits and updates origin/main but leaves your files alone, so you can inspect them first. pull is fetch plus merge (or rebase, with --rebase) into your current branch.

git revert vs git reset?

revert creates a new commit that undoes an earlier one. History is preserved, so it's safe on shared branches. reset moves the branch pointer backwards and can discard commits (--hard also discards file changes). It rewrites history, so use it only on unpushed work.

A deployed model API broke after the latest commit. How do you roll back quickly?

Find the last good commit (git log), git revert the bad commit(s), and push. CI/CD then rebuilds and redeploys the known-good code. If images are tagged by commit SHA, you can also redeploy the previous image immediately while the revert goes through CI.

Your push is rejected with "Updates were rejected… fetch first". Why, and what do you do?

Someone else pushed commits you don't have. Run git pull (or git pull --rebase), resolve any conflicts, run the tests, then push again. Never force-push over a shared branch to "fix" this.

What is a commit hash?

A SHA-1 (or SHA-256 in newer setups) checksum computed from the commit's content, its parent(s), author and message. It uniquely identifies the snapshot, and any change produces a different hash, which is what makes Git history tamper-evident. MLOps tools record it so a model can be traced to its exact code.

13Recap

  • Sharing zips doesn't scale. Commit and push to GitHub, and teammates pull.
  • git status shows untracked, modified and staged files (VS Code shows the same as badges).
  • git add file or git add . stages changes. git commit -m "msg" saves a version, after which Git tracks the file.
  • git push origin main uploads to GitHub (origin = remote, main = default branch). git pull downloads others' work.
  • Each commit has a hash ID. On GitHub, open the commit history and Browse the repository at this point to see old code. Locally, use git restore --source or git revert, not git pull.
