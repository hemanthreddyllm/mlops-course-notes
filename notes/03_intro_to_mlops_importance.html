01The use case 41:10

You're a data scientist at ESPNcricinfo, a website with cricket scores and stats. It has a Live Forecast feature: from the runs scored so far and the teams' past scores, it predicts the final score after 20 overs, in real time.

Assume the feature doesn't exist yet and you've been asked to build it.

Problem type

Regression. The target is a number (runs after 20 overs).

Inputs

Historical scores for all teams, the live score, player run history and performance, and many more possible features.

Domain

Sports data. It changes during a match and from season to season.

Plan of the chapter

First build it without MLOps. Then list what goes wrong. Then see how MLOps fixes each problem.

03Building it the traditional way 45:22

Who is on the team?

Front-end developer

Builds the forecast widget on the page with HTML and CSS: the icon, the text, the predicted score.

Data scientist (you) → back end

Builds the model and an API. Live scores are sent to the model, and predictions go back to the front end.

The traditional flow

Beyond the video · what the "API" box looks like

A minimal version of the API step, so you can picture the serving layer. The course builds a proper version later.

# app.py: load the pickled model once and serve predictions over HTTP
import pickle
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()
with open("model.pkl", "rb") as f:          # traditional: file pulled from S3 by hand
    model = pickle.load(f)

class MatchState(BaseModel):
    current_runs: int
    overs_done: float
    wickets: int

@app.post("/predict")
def predict(s: MatchState):
    pred = model.predict([[s.current_runs, s.overs_done, s.wickets]])[0]
    return {"projected_score_20_overs": round(float(pred))}

# run:  uvicorn app:app --host 0.0.0.0 --port 8000

04What breaks in production 48:32

The app is live. But the model was evaluated on historical test data, and live match data has a different distribution. Models do well on test data and then become biased on real-time data. The forecasts are badly off:

Your manager asks you to fix it. You decide the model needs richer, fresher data:

Data neededWhyWhere it comes from
Historical dataStill important as a base (e.g. everything up to 2024)Database
Real-time / current dataCurrent season and month, plus live ball-by-ball scoresStreaming service
Weather dataGood weather tends to mean higher scores, bad weather lowerExternal APIs

The traditional build only read one CSV or database. Now both the data distribution and the ingestion process have changed. That leads to the first problem.

P1Data problem 52:08

Without MLOps

Data now comes from a database, a streaming service and APIs. You write and maintain separate fetch code for each, by hand, every time something changes.

With MLOps

Build an ETL (Extract–Transform–Load) pipeline into one data warehouse, a common point. Wherever the data comes from, it ends up in the same place, and data scientists, analysts and anyone else read from there.

Tools: for streaming, Apache Kafka. For big-data storage and processing, Hadoop, among others.

P2Code implementation problem 54:14

Traditionally, one file does everything: imports → load data → preprocess → train/test split → train → evaluate → print accuracy. A real system has separate components, and putting them all in one file causes trouble:

Issue with a single fileWhat it means
Hard to maintainThe file becomes huge.
Limited reusabilityA new feature means rewriting code from scratch.
Harder collaborationIn industry many developers each own a task, and they can't all work in one file.
Poor scalabilityAdding new features later is painful.
Testing challengesFinding and fixing bugs is hard.

Fix: modular coding. Use Python OOP (classes) so each component lives in its own file. Generate the folder structure automatically, either with cookiecutter or with your own template.py script (the course writes its own). Then the person working on ingestion only touches the ingestion file, the person on training only touches the trainer, and so on.

Typical modular project layout

project/
├── src/
│   ├── components/
│   │   ├── data_ingestion.py
│   │   ├── data_validation.py
│   │   ├── data_transformation.py
│   │   ├── model_trainer.py
│   │   └── model_evaluation.py
│   ├── pipeline/
│   │   ├── training_pipeline.py
│   │   └── prediction_pipeline.py
│   ├── config/ · entity/ · utils/
│   ├── logger/ · exception/
├── notebooks/        # EDA lives here
├── app.py            # serving
├── requirements.txt
├── Dockerfile

What template.py does

# template.py: create the project skeleton in one go
from pathlib import Path

files = [
  "src/__init__.py",
  "src/components/data_ingestion.py",
  "src/components/data_validation.py",
  "src/components/data_transformation.py",
  "src/components/model_trainer.py",
  "src/components/model_evaluation.py",
  "src/pipeline/training_pipeline.py",
  "src/pipeline/prediction_pipeline.py",
  "app.py", "requirements.txt",
]
for f in map(Path, files):
    f.parent.mkdir(parents=True, exist_ok=True)
    f.touch(exist_ok=True)
Important nuance from the instructor

MLOps does the same steps as ML (ingestion, preprocessing, training). The difference is that they are automated and structured instead of done by hand. You can build an app without MLOps, but it will be hard to maintain and hard to scale.

P3Version problem 59:27

Without MLOps

  • You add a feature, overwrite the code, and lose the previous working version.
  • The new version has bugs and you can't roll back.
  • Many developers on different machines push changes that conflict.

With MLOps

Git + GitHub for code management. Every version is kept, and you can go back at any time. This matters most in big teams and on frequently updated projects.

Real example: TensorFlow. The instructor opens TensorFlow's GitHub repo and shows many branches and release versions, with the last commit only 17 minutes earlier. The PyPI page shows a long release history. The package was never built "in one shot". It changes every day, and old versions stay available.

P4Experiment problem 1:01:31

Recall the research room from the analogy: experiments are how you keep getting a better model. In ML this is mostly hyperparameter tuning (different parameters, different learning rates, different algorithms).

The trap

Run an experiment, overwrite the previous one, and lose the history. You can no longer tell which setting was best.

The fix: experiment tracking with MLflow

Record every experiment (Exp 1, Exp 2, Exp 3…): its parameters, metrics and model file. Then compare them and choose the best.

Beyond the video · the MLflow calls you'll use 
import mlflow
with mlflow.start_run(run_name="exp-3"):
    mlflow.log_params({"n_estimators": 300, "max_depth": 12})
    model.fit(X_train, y_train)
    mlflow.log_metric("rmse", rmse)
    mlflow.sklearn.log_model(model, "model")   # saved with the run and can be registered

P5Deployment problem 1:03:37

Manual deployment causes downtime

With the traditional setup, every change (such as adding the forecast feature) means: stop the server → update the code → start the server. While it's down, users see "site is down", have a bad experience and may not come back. Modern sites ship new features while staying up, and they do it with CI/CD.

"It works on my machine": why Docker

Locally the code runs because every dependency is installed at the right version. On a cloud server, a package might be missing or at a different version, and the app fails. Docker packages the app and its environment into an image that runs the same way on any server. The course uses Docker to build the whole deployment pipeline.

Beyond the video · a minimal Dockerfile for the API above 
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]

Tools: CI/CD with Jenkins, CircleCI, GitHub Actions; cloud with AWS / GCP (for example ECR as the image registry); containers with Docker.

P6Data drift problem 1:05:44

Data drift means the data distribution the model was trained on differs from the distribution it sees in production, so performance drops. This is exactly what happened with the cricket model: it was trained on historical data and then received live data that looked different.

1 · Monitor

Watch the live app and its input and prediction distributions with Grafana and Evidently.

2 · Detect

Is drift happening? Evidently compares training and live data statistically.

3 · Update data

Fix the data pipeline, for example by adding real-time and current-season data.

4 · Retrain

Run the retraining pipeline so the model learns the new distribution, then redeploy.

P7Infrastructure problem 1:07:49

The whole pipeline has to be hosted on a cloud platform: AWS, GCP or Azure. If you don't understand their services, you can end up with very large bills. The instructor points out that most companies spend a large share of their money on cloud servers, paid every month.

What to learn

Which cloud services exist, how to use them, and how to manage them properly to reduce cost: pick the right instance size, shut down what you don't use, and so on. The course covers cloud fundamentals at 3:09:31 and uses EC2, S3, ECR and SageMaker in the projects.

P8Automation problem 1:08:51

Traditionally you work in notebooks or loose files and run and update each part by hand. With MLOps, the components run as a pipeline in a fixed order:

Tool: DVC for pipeline tracking. It defines the stages and their order and re-runs only what changed, which automates the whole application.

Beyond the video · a peek at a DVC pipeline 
# dvc.yaml: each stage declares its command, inputs (deps) and outputs (outs)
stages:
  ingest:
    cmd: python src/components/data_ingestion.py
    outs: [data/raw]
  train:
    cmd: python src/components/model_trainer.py
    deps: [data/raw, src/components/model_trainer.py]
    outs: [models/model.pkl]
# run the whole thing:  dvc repro

P9Legal / governance problem 1:09:53

An application also has to handle legal, security and governance concerns. The instructor gives two examples:

ChatGPT-style assistant

If someone asks how to build something dangerous, the app should not answer, or it gets used for harm. Harmful requests need guardrails.

Our sports forecaster

People could use the predictions for illegal betting, a very large illegal business. If you ignore that, you could end up in court and spend a lot of money on the app.

The traditional approach doesn't address this. MLOps practice includes governance, security and compliance as part of the lifecycle.

08Interview questions

Walk me through the problems of deploying an ML model without MLOps.

Use the 9-problem list: (1) data from many sources with no central store, (2) monolithic notebook code that is hard to maintain, reuse, test or scale, (3) no versioning, so no rollback, (4) experiments not tracked, (5) manual deployment with downtime and environment mismatch, (6) data drift nobody notices, (7) unmanaged cloud infrastructure and cost, (8) no pipeline automation, (9) legal and governance risks. Pair each with its fix: ETL + warehouse, modular OOP code, Git, MLflow, CI/CD + Docker, monitoring + retraining, cloud skills, DVC pipelines, governance.

What is data drift and how do you handle it?

The input data distribution in production differs from the training distribution (for example, live scores trend higher than historical ones), so accuracy degrades even though the code is unchanged. Handle it by monitoring input and prediction distributions (Evidently, Grafana), alerting when statistical tests show a shift, updating the data pipeline to include fresh data, and running a retraining pipeline followed by a CI/CD redeploy.

Why use Docker for ML deployment?

It packages code plus exact dependency versions into one image, so the model behaves the same on a laptop, a CI runner and a cloud server. It removes the "works on my machine" failures and is the unit that CI/CD builds, pushes to a registry (such as ECR) and deploys.

Why write modular code instead of a notebook?

Maintainability, reusability, parallel collaboration, scalability and testability. Each component (ingestion, validation, transformation, trainer, evaluation, prediction) is a separate class or file, owned and tested on its own and wired together as a pipeline.

How does CI/CD avoid downtime compared with manual deployment?

Manual deployment means stopping the server, updating it and restarting, so the site is down in between. With CI/CD, a git push triggers automated tests and an image build. The new version is rolled out while the old one keeps serving, and traffic moves over only when the new one is healthy.

What are the benefits and challenges of MLOps?

Benefits: scalability, performance, reproducibility, collaboration, risk reduction, cost savings, faster time to market, compliance and governance. Challenges: model complexity (variability, black boxes), data quality, cost, scale, security, regulation, integration with existing systems, and the skill gap (ML + data engineering + DevOps).

Is experiment tracking the same as hyperparameter tuning?

No. Tuning is the search over parameters. Tracking is recording every run's parameters, metrics and artifacts so you can compare them, reproduce them and promote the best one. You tune and track at the same time, and MLflow handles the tracking.
