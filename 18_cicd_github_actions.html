01The problem with manual deployment 07:20:17

So far the workflow has been: develop on your laptop (the development environment), push the code to GitHub with git, and deploy by hand. For example, you launch an EC2 machine, copy the project there and start it. That gives you an endpoint users can reach.

Now, 4–6 months later, you want new features. The instructor's example is the medical chatbot from his other course, getting new data and knowledge. By hand, you would:

The idea in one line

Don't deploy by hand. Push the code to GitHub, and a CI/CD tool automatically tests, packages and deploys it to the cloud, while users keep using the app.

02CI, continuous delivery, continuous deployment

The course expands CI/CD as "continuous integration, continuous delivery or deployment". The two meanings of CD are different:

StageWhat it meansIn the course workflowIn our workflow
Continuous integration (CI)every push is merged and automatically checked: build, lint, testsjob "Continuous Integration": only echo "Linting…" and echo "Running unit tests"install deps → dvc repro model_building → pytest
Continuous deliveryevery change that passes CI becomes a releasable artifact, ready to deploy; the release itself may still need a clickjob "Continuous Delivery": build the Docker image and push it to ECRsame, tagged with the commit SHA and latest
Continuous deploymentthat artifact goes to production automatically, with no human approvaljob "Continuous-Deployment" on EC2: pull and docker runpull, replace the container, smoke test

The course pipeline does all three, because nothing stops a green build from going live. Many teams put a manual approval (a GitHub environment with required reviewers) between delivery and deployment.

Something has to notice the push and run the steps. That's a CI/CD automation tool. The instructor names the three most popular:

Small correction

The video says Jenkins and CircleCI need a server you set up yourself. That's true for Jenkins. CircleCI is a cloud service: you sign in with GitHub and add a config file. (In the course's CircleCI demo, EC2 is still used, but only as the deployment target or runner.)

Whichever tool you use, the pipeline has the same shape: trigger → test → build image → push to a registry → deploy. Once you know GitHub Actions well, the other two are mostly different syntax.

07AWS set-up: IAM user, ECR, EC2 with Docker 07:26:49

  1. Log in to the AWS console. Pick a region and stick to it; the video uses Mumbai, ap-south-1.

  2. IAM user (e.g. ml-project) → attach policies directly:

    • AmazonEC2ContainerRegistryFullAccess (ECR)
    • AmazonEC2FullAccess (EC2)

    Create the user → Security credentials → Create access key → Command Line Interface → download the CSV. Its access key ID comes before the comma and the secret key after it. "Don't share this key with anyone."

  3. ECR repository: search "Elastic Container Registry" → Create repository → name it (e.g. ml-project) with default settings → copy the URI, e.g. 123456789012.dkr.ecr.ap-south-1.amazonaws.com/ml-project.

  4. EC2 instance (ml-machine):

    • Ubuntu, t2.large ("take at least 8 GB memory")
    • a key pair (only needed for third-party SSH tools such as PuTTY or MobaXterm)
    • allow HTTP and HTTPS, 30 GB storage

    Launch it, wait for Running, then open Connect for a browser terminal. "This is your production server."

  5. Install Docker on the instance (from the repo README):

    sudo apt-get update -y
sudo apt-get upgrade                           # optional
curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
sudo usermod -aG docker ubuntu                 # docker without sudo
newgrp docker
docker --version                               # a version number means Docker works

08EC2 as a self-hosted runner 07:32:23

This connects GitHub to the EC2 machine, so the deployment job runs there.

  1. In your repo: Settings → Actions → Runners → New self-hosted runner → choose Linux.
  2. Copy the Download commands one by one into the EC2 terminal: make a folder, download the runner archive, extract it.
  3. Copy the Configure command (./config.sh --url … --token …). It authenticates with GitHub and then asks:
    • runner group → Enter
    • runner name → the instructor types self-hosted ("make sure you give the same name")
    • labels → Enter; work folder → Enter
  4. Run ./run.sh → "Connected to GitHub … Listening for Jobs".
  5. Back on the Runners page, the runner shows as Idle: connected and waiting.
Two things the video doesn't cover
  • The runner name isn't what matters. runs-on: self-hosted matches the label self-hosted, which every self-hosted runner gets automatically, along with Linux and X64. Any name works.
  • ./run.sh stops when the browser terminal closes. Install the agent as a service so it survives logouts and reboots: sudo ./svc.sh install && sudo ./svc.sh start. The registration token is short-lived (about an hour), so use it straight away.

10Push, watch the run, open port 8080 07:37:05

  1. Commit and push (the instructor's message is "cicd added"). The repo page shows a yellow dot, meaning a workflow is running. Open the Actions tab to see the run and its three jobs.

  2. Continuous Integration finishes almost instantly, because it only echoes.

  3. Continuous Delivery takes a few minutes: install utilities → AWS authentication → build the image → push it to ECR. Afterwards the image appears in the ECR repository.

  4. Continuous Deployment runs on EC2: authenticate again → pull the image from ECR → docker run -d -p 8080:8080 --name=cnncls ….

  5. Opening http://<public-ip> fails at first, because port 8080 isn't open. Instance → Security → security group → Edit inbound rules → Custom TCP, 8080, 0.0.0.0/0 → Save.

  6. Open http://<public-ip>:8080 and the app loads: the course's wine-quality demo (not the YouTube project). Open /train ("Training Successful!"), then enter feature values and click Predict to get a wine-quality score.

        12Deploying again, and cleaning up 07:40:14

        The second push

        The instructor's warning: before pushing a second time, uncomment the three "Stop and remove container" lines in the deployment job. The container name cnncls is already taken, so a second docker run --name=cnncls fails with "Conflict. The container name is already in use". With the lines enabled, the job stops and removes the old container, then starts the new one. The set-up itself is one-time: after that, every change reaches AWS on its own.

        # in the course file (commented out)
- name: Stop and remove container if running
  run: |
    docker ps -q --filter "name=cnncls" | grep -q . \
      && docker stop cnncls && docker rm -fv cnncls

        Even uncommented, this line has a flaw: if the container exists but is stopped, docker ps -q (running only) finds nothing, and the run fails again. docker rm -f cnncls || true handles both cases.

        Delete everything 07:40:14

        "Otherwise it will charge you."

        1. EC2 → select → Instance state → Terminate (it shows shutting down, then disappears).
        2. ECR → delete the repository.
        3. IAM → delete the user (type its name to confirm).

        Also:

        • Remove the offline runner in GitHub (Settings → Actions → Runners). Otherwise the next push's deploy job waits in the queue forever.
        • Delete the now-useless secrets.

        13Precision notes

        • CI that doesn't test isn't CI. The course's CI job only echoes, so a broken app still goes live. Run real checks there: lint, unit tests, API tests and a model-quality gate. Our Chapter 17 workflow runs pytest after rebuilding the model.
        • Outdated actions and commands (actionlint flags all of them):
          • actions/checkout@v3 and configure-aws-credentials@v1 use Node versions GitHub has retired → @v4
          • amazon-ecr-login@v1 → @v2
          • ::set-output is deprecated → echo "name=value" >> "$GITHUB_OUTPUT"
        • Long-lived access keys. The file already sets permissions: id-token: write, which is what OIDC needs, but still uses static keys. With OIDC, AWS trusts GitHub's short-lived token (role-to-assume: arn:aws:iam::…:role/gha-deploy), so no keys are stored anywhere.
        • Over-broad policies. AmazonEC2FullAccess isn't needed by the pipeline at all. The keys only push to and pull from ECR. On EC2, give the instance an instance role with ECR read access instead of keys.
        • AWS keys passed into the container (docker run -e AWS_ACCESS_KEY_ID=… -e AWS_SECRET_ACCESS_KEY=…). The wine app doesn't need them, and anyone who can run docker inspect on the host can read them.
        • Only the :latest tag. You can't tell which commit is live or roll back to an earlier build. Tag with ${{ github.sha }} as well; our workflow does.
        • Downtime still happens. The video says CI/CD keeps the app running while features ship. Automation removes the hours of manual work, but stop-then-start on one server still drops requests for a few seconds. True zero-downtime needs rolling or blue/green deployment behind a load balancer (ECS, Kubernetes, App Runner).
        • Self-hosted runners on public repos are dangerous. A pull request from a fork could run code on your EC2 machine. GitHub recommends self-hosted runners only for private repos, or with strict fork-PR approval.
        • The runner name self-hosted isn't required; the label is what matches (see section 8).
        • The region must match everywhere: ECR repo, AWS_REGION, AWS_ECR_LOGIN_URI. The video uses ap-south-1 while the README example says us-east-1.
        • Everything as a secret. The region and repo name aren't sensitive. Secrets get masked in logs, and GitHub drops any job output that contains a secret value. Keep non-sensitive settings in variables (vars.*).
        • The wine app runs Flask with debug=True on 0.0.0.0, and its GET /train runs os.system("python main.py") inside the production container. Training belongs in the pipeline (CI or a scheduled job), not behind a public GET endpoint.
        • Cost. t2.large isn't free-tier. Terminate it right after the demo, as the instructor does.

        14Interview questions

        Explain CI vs continuous delivery vs continuous deployment.
        • CI: every change is integrated often and automatically checked (build and tests).
        • Continuous delivery: every change that passes CI becomes a deployable artifact (e.g. an image in a registry), and release is one click away.
        • Continuous deployment: that release also happens automatically, with no human gate.
        What does CI/CD look like for an ML project, compared with normal software?

        On top of the usual code tests, ML CI checks the things that can break a model:

        • Data: schema and quality checks.
        • Training: a reproducible pipeline run (DVC, dvc repro).
        • Quality gate: the model must beat a threshold or the current production model.
        • Serving: signature and API contract tests.

        CD ships the model (registry version or image) plus the serving code, often with canary or shadow rollout and monitoring. Retraining can be triggered by a schedule or by data drift ("continuous training").

        GitHub-hosted vs self-hosted runners: when would you use each?

        GitHub-hosted runners give you a fresh, maintenance-free VM for every job: good for tests and builds. The downsides are cost per minute on private repos and no access to your private network.

        Self-hosted runners are machines you control, and suit:

        • access to private resources (e.g. deploying on the same host)
        • GPUs or large machines
        • caching

        The trade-off: you patch them and secure them. They're risky on public repos, and state can leak between jobs. For per-job isolation use ephemeral runners.

        How do you give a GitHub workflow access to AWS securely?

        Use OIDC:

        1. Create an IAM identity provider for token.actions.githubusercontent.com.
        2. Create a role whose trust policy is limited to your repo and branch (e.g. repo:me/app:ref:refs/heads/main), with least-privilege permissions (push to one ECR repo).
        3. In the workflow, set permissions: id-token: write and use configure-aws-credentials with role-to-assume.

        No long-lived keys are stored, and the credentials expire in about an hour.

        How do you roll back a bad deployment in this setup?

        Tag every image with the commit SHA (keep latest as a convenience). To roll back, run the deploy step with the previous SHA tag, via workflow_dispatch with an input or by reverting the commit. With only :latest you would have to rebuild old code. On ECS or Kubernetes, you roll back to the previous task definition or ReplicaSet.

        How do you pass data between jobs?

        Jobs run on separate machines, so nothing is shared by default.

        • Small values: job outputs, read later via needs.<job>.outputs.x. Outputs containing secrets are dropped.
        • Files: actions/upload-artifact and download-artifact (our model files).
        • Large or shared data: a registry, S3 or a cache.
        Your deploy job has been "Queued" for an hour. Why?

        No runner with the required labels is online: the EC2 instance is stopped or terminated, run.sh died when the terminal closed (install it as a service), the runner was removed, or it belongs to another repo or org. Check Settings → Actions → Runners.

        How would you avoid downtime during deployment?

        Start the new version first, health-check it, then switch traffic and stop the old one. That's blue/green, or a rolling update of several replicas behind a load balancer. Managed platforms (ECS with an ALB, Kubernetes Deployments, App Runner, SageMaker endpoints) do this for you. A single docker stop/docker run on one host always has a short gap.

        How do you keep secrets safe in CI?
        • Store them as encrypted secrets, scoped to an environment with required reviewers for production.
        • Prefer OIDC to static keys.
        • Grant least privilege, and rotate secrets.
        • Never echo them or bake them into images.
        • Restrict who can edit workflows (branch protection, CODEOWNERS).
        • Pin third-party actions to a commit SHA, so a compromised action tag can't steal secrets.

        15Recap

        • Why: manual redeploys mean downtime and toil. With CI/CD, a git push automatically tests, packages and deploys.
        • CI checks the code. Delivery produces a releasable image in a registry. Deployment puts it live automatically.
        • Tools: GitHub Actions (built in; used here), Jenkins (a server you run), CircleCI (SaaS).
        • Workflow .github/workflows/cicd.yaml: on push to main → job 1 CI (ubuntu-latest) → job 2 build and push to ECR → job 3 on the self-hosted EC2 runner: pull and docker run -p 8080:8080.
        • AWS: an IAM user (ECR + EC2 policies, access key CSV), an ECR repo (copy the URI), EC2 Ubuntu t2.large with 30 GB and Docker installed.
        • GitHub: Settings → Actions → Runners → New self-hosted runner (download, config.sh, run.sh → Idle). Five secrets: keys, region, ECR login URI, repo name.
        • Run: push → watch Actions → image in ECR → open inbound 8080 → app at ip:8080. Before the next push, enable the stop/remove step. Afterwards, terminate EC2 and delete the ECR repo and IAM user.
